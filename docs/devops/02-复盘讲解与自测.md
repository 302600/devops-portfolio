## 一、先建立全局认知（这个项目到底做了什么）

### 1.1 用"开一家自动化工厂"来理解整个项目

别把这套东西想得太玄。它本质就是一条**自动化生产流水线**，只不过生产的不是零件，而是"能对外提供服务的网页应用"。

我们拿"开一家会自动上货的工厂"来打比方：

- **你（开发/运维）** = 工厂设计师，负责改图纸（改代码）。
- **Git 仓库（Gitea）** = 图纸档案室，所有图纸的最新版本都存这里，谁改了、改了啥都有记录。
- **镜像构建（buildkit / nerdctl build）** = 车间里的生产机器，把图纸（代码 + Dockerfile）加工成一个标准化的"集装箱货物"（镜像）。
- **镜像仓库（Harbor）** = 成品仓库，加工好的集装箱都堆在这里，贴好标签（tag）等着发货。
- **部署清单（deployment.yaml）** = 一张"发货单"，写清楚"这次要发哪个版本的货、发几箱"。
- **ArgoCD** = 一个尽职的仓库管理员，他**盯着图纸档案室**，只要发现发货单变了，就自动按新发货单去调度上货。
- **Kubernetes（K8s）** = 整个工厂的调度中枢+货架系统，负责把集装箱真正摆到货架上、坏了自动换新、按需要摆几箱就摆几箱。
- **Ingress** = 工厂的对外大门+前台，顾客（用户浏览器）从这个门进来，前台按"你要找哪个部门"把人领到对应货架前。

一句话总结：**改代码 → 存进 Git → 打包成镜像 → 推到镜像仓库 → 改发货单 → ArgoCD 发现后自动上货 → K8s 跑起来 → 用户通过 Ingress 访问。**

### 1.3 一句话说清 CI 和 CD

很多人把 CI/CD 混着说，面试要能拆清楚：

- **CI（Continuous Integration，持续集成）**：管的是"**从代码到镜像**"这一段。即：改完代码 → 自动构建 → 打包成镜像 → 推到镜像仓库。**在我们项目里，这段目前是半自动**（用 nerdctl build 手动构建、手动推 Harbor；Jenkins 已装但 CI 自动化没完全接入，这点面试要如实说）。
- **CD（Continuous Delivery/Deployment，持续交付/部署）**：管的是"**从镜像到线上运行**"这一段。即：部署清单一变，就自动把新版本部署到 K8s。**在我们项目里，这段是全自动的，由 ArgoCD 负责（GitOps 模式，已完整跑通）**。

一句话话术：**"CI 负责把代码变成镜像，CD 负责把镜像变成线上服务。我的项目里 CD 用 ArgoCD 做了 GitOps 全自动，CI 目前是手动构建推仓库、Jenkins 装了但还没完全接入自动化。"**（诚实回答，反而显得靠谱。）

### 2.1 云服务器 ECS 与按量付费

**【是什么】**
ECS（Elastic Compute Service，弹性计算服务）就是阿里云上的一台"云端电脑"。你不用自己买物理服务器、不用找机房，在网页上点几下，就能开一台带公网 IP 的 Linux 服务器，SSH 连上去就能用。我们用的配置是：4 核 CPU、16G 内存、Rocky Linux 10.2 系统。

**【为什么需要它】**
K8s、Harbor、Jenkins 这些东西都很吃内存，个人电脑装虚拟机跑单节点会很卡，而且没有公网 IP 别人访问不了。云服务器解决了"随时可用、有公网 IP、配置够大"的问题。

**【在我们项目里怎么用】**
所有组件都装在这一台 ECS 上（单节点）。我们特意选了**按量付费（用多少小时算多少钱）**而不是包年包月，因为这是学习/搭建用途，搭完、验证完就可以释放，成本可控。成本控制思路：① 按量付费按小时计费，不用时关机/释放；② 别误选带 GPU 的机型（贵好几倍，我们一开始踩过这个坑）；③ 选够用的规格即可，4核16G 跑单节点最小版正好。

**【面试怎么答】**
> "项目部署在一台阿里云 ECS 上，4核16G、Rocky Linux。我用的是按量付费而不是包年包月，因为是学习验证场景，按小时计费、用完能释放，成本可控。生产环境如果长期跑，才会考虑包年包月更划算。"

### 2.2 Linux 系统初始化

**【是什么】**
拿到一台全新的服务器后，在装任何软件之前要做的"打扫房间"工作：关掉会捣乱的安全策略、对好时间、换成快的软件下载源。

**【为什么需要它】**
默认配置经常会挡住 K8s 和容器：防火墙可能拦端口、SELinux 可能拦容器操作、时间不准会导致证书校验失败、默认软件源在国外下载慢甚至连不上。不初始化好，后面装什么都容易出莫名其妙的错。

**【在我们项目里怎么用】**
主要做了这几件事：
- **防火墙**：单节点学习环境，关掉 firewalld（或放行必要端口），避免拦住 K8s 内部通信。
- **SELinux**：设为 permissive/disabled，避免它拦住容器读写文件（很多 K8s 教程都要求这步）。
- **时间同步**：用 chronyd/ntp 对时，保证证书、日志时间正确。
- **软件源**：把系统源和后面用到的 Docker 源都换成**阿里云镜像源**（因为官方源在国内慢/被墙，我们后面专门踩过这个坑）。

**【面试怎么答】**
> "装 K8s 前我会先做系统初始化：关防火墙或放行端口、把 SELinux 设成宽容模式、配置时间同步、把 yum 源和容器源换成国内镜像源。这几步能避免后面装组件时出网络和权限的怪问题。"

### 2.3 容器与镜像（Docker vs containerd vs nerdctl）

**【是什么】**
- **容器**：一个"打包好的、隔离的运行环境"。可以理解成一个**标准集装箱**——里面装着你的应用和它需要的所有依赖（库、配置），搬到哪台机器上都能一样地跑起来，不会出现"在我电脑上能跑、到服务器就挂"的问题。
- **镜像（image）**：容器的"**模板/快照**"。容器是"跑起来的镜像"，镜像是"静止的容器"。类比：镜像是"菜谱+半成品"，容器是"照着做出来的那盘菜"。
- **Docker**：最出名的容器工具，既能构建镜像、又能跑容器，还带一堆命令行工具，是个"全家桶"。
- **containerd**：Docker 底层真正干活的那个"核心引擎"。后来它被单独拆出来，成了一个更轻量、更专注于"跑容器"的运行时。
- **nerdctl**：containerd 的命令行工具，命令几乎和 docker 一模一样（`nerdctl build`、`nerdctl run`），让你在只有 containerd 的机器上也能像用 docker 一样操作。

**【为什么需要它 / 为什么 K8s 用 containerd】**
K8s 早期通过一个叫 dockershim 的"转接头"来调用 Docker，但 Docker 是个大而全的全家桶，K8s 其实只需要它的核心运行时部分。为了更轻量、更标准（遵循 CRI 接口规范），**K8s 从 1.24 版本开始移除了 dockershim，改成直接用 containerd 这类符合 CRI 标准的运行时**。所以现在新装的 K8s 默认底层就是 containerd，不再需要装完整 Docker。

**【在我们项目里怎么用】**
我们的 K8s（v1.31.9）底层容器运行时就是 **containerd**，日常用 **nerdctl** 来构建和管理镜像（比如 `nerdctl build` 打包我们的 nginx 网页应用）。我们没有装完整的 Docker，还专门处理过"containerd 和 Docker 冲突"的坑。

**【面试怎么答】**
> "容器就是把应用和依赖打包成标准集装箱，到哪都能一致地跑；镜像是容器的模板。K8s 现在底层用 containerd 而不是 Docker，因为 Docker 太重、K8s 只需要核心运行时，从 1.24 起移除了 dockershim。我项目里就是 containerd + nerdctl，nerdctl 命令和 docker 基本一样。"

### 2.4 镜像与镜像加速（registry / mirror）

**【是什么】**
- **镜像仓库（registry）**：专门存镜像的"仓库/网盘"，比如官方的 Docker Hub、我们自建的 Harbor。你 `push` 镜像上去、`pull` 镜像下来。
- **镜像加速（mirror）**：因为官方仓库（Docker Hub）在国外，国内拉取又慢又容易失败，所以配一个"**国内的镜像加速地址**"（相当于国内的中转下载站），拉镜像时先从这个快的地方拉。

**【为什么需要它 / 为什么国内要配加速】**
国内直连 Docker Hub 经常超时、失败。配了阿里云等提供的镜像加速地址后，拉公共镜像（如 nginx:alpine）会快很多、稳很多。这是国内做容器几乎必配的一步。

**【在我们项目里怎么用】**
这里有个**重要的坑点认知**：containerd、buildkit、docker **是三套不同的程序，各自读各自的配置文件**，所以镜像加速要**分别配三套**，不能只配一个就以为全生效了：
- containerd：改 `/etc/containerd/` 下的 registry 配置（hosts.toml 等）。
- buildkit：有自己独立的镜像加速/registry 配置，构建时才用得上。
- docker（如果装了）：改 `/etc/docker/daemon.json`。

我们还踩过"**镜像加速地址失效**"的坑——某些老的加速地址已经停用了，要换成当前可用的。

**【面试怎么答】**
> "镜像仓库就是存镜像的地方，国内拉官方镜像慢，所以要配镜像加速。我踩过一个坑：containerd、buildkit、docker 是三套独立的程序，镜像加速要分别配三份，只配一个不生效；另外有的加速地址失效了要换新的。"

### 2.5 Kubernetes 核心概念

**【是什么】**
Kubernetes（简称 K8s，"K" 和 "s" 中间 8 个字母）是一个**容器编排系统**——你给它一堆容器，它帮你自动安排"在哪台机器跑、跑几个、挂了自动重启、要升级平滑升级"。可以理解成**容器的"大管家/调度中枢"**。

核心概念（务必分清）：

- **Pod**：K8s 里**最小的调度单位**。一个 Pod 里装一个或几个"关系特别近"的容器，它们共享网络和存储。可以把 Pod 理解成"一个小房间，里面住着紧密协作的容器"。注意：**K8s 不直接管容器，而是管 Pod**。
- **ReplicaSet（副本集）**：负责"保证某个 Pod 始终有 N 个副本在跑"。挂了一个就补一个。一般不直接用它，而是被 Deployment 管着。
- **Deployment（部署）**：最常用的控制器，管理"我要跑几个副本、用哪个镜像、怎么滚动升级/回滚"。你改 Deployment，它就通过 ReplicaSet 去调整 Pod。**它是"发货单"的载体。**
- **Service（服务）**：给一组 Pod 提供一个**固定的访问入口**（固定 IP + 固定名字）。因为 Pod 会死会重建、IP 会变，所以要用 Service 做稳定入口。
- **Namespace（命名空间）**：把集群"分成几个逻辑房间"，用来隔离不同项目/环境（比如 harbor、argocd、我们的应用各在自己的命名空间），避免互相干扰、方便管理权限。

**两个重要思想（面试常考）：**
- **控制器模式**：K8s 里到处是"控制器"，它们干一件事——**不断对比"你想要的状态"和"当前实际状态"，有差就去纠正**。就像空调：你设 26 度（期望），它不停测室温（实际），不到就继续吹。
- **声明式（Declarative）**：你不告诉 K8s"具体怎么一步步做"，而是写一份 YAML **描述"我最终想要什么样"**（比如"我要 2 个 nginx 副本、用 v2 镜像"），K8s 自己想办法达成。对应的"命令式"是你一条条下命令。声明式的好处：可以存进 Git、可重复、可追溯——这正是 GitOps 的基础。

**【为什么需要它】**
容器多了以后，手动管（哪台机器跑、挂了重启、升级、扩容）根本管不过来。K8s 把这些全自动化了，还能自愈、自动扩缩容、平滑升级。

**【在我们项目里怎么用】**
我们用 Sealos 装了单节点 K8s v1.31.9。示例应用就是：一个 **Deployment** 跑我们的 nginx 网页镜像，配一个 **Service** 做稳定入口，再用 **Ingress** 对外暴露；各组件分别放在自己的 **Namespace** 里。

**【面试怎么答】**
> "K8s 是容器编排系统，帮你自动调度、自愈、扩缩容、滚动升级。核心对象里 Pod 是最小单位，Deployment 管副本和升级回滚，Service 给 Pod 提供固定访问入口，Namespace 做隔离。它的核心思想是声明式+控制器模式：我写 YAML 描述期望状态，控制器不停地把实际状态往期望状态上纠。"

### 2.6 K8s 集群组件（控制面 + 节点组件）

**【是什么 / 各干什么】**
K8s 集群分"**控制面（大脑，管决策）**"和"**节点组件（手脚，管干活）**"。单节点情况下这些都挤在同一台机器上。

控制面（Control Plane）：
- **etcd**：集群的"**账本/数据库**"，存着整个集群的所有状态数据（有哪些 Pod、配置是什么）。它是 K8s 的记忆，非常关键，坏了集群就懵了。
- **kube-apiserver**：集群的"**总前台/唯一入口**"。所有人（kubectl、各组件）想操作集群，都得通过它。它负责校验请求、读写 etcd。**所有组件之间不直接对话，都通过 apiserver 中转。**
- **kube-scheduler（调度器）**：负责"**新 Pod 该放到哪个节点上跑**"的决策（看哪个节点资源够、条件合适）。
- **kube-controller-manager（控制器管理器）**：里面跑着一堆控制器（如前面说的 ReplicaSet 控制器），**不停地把实际状态往期望状态纠**。

节点组件（每个工作节点上都有）：
- **kubelet**：节点上的"**领班**"。听 apiserver 的指令，负责在本节点上真正把 Pod 拉起来、监控它、汇报状态。它直接和 containerd 打交道。
- **kube-proxy**：负责节点上的"**网络转发规则**"，让 Service 的访问能正确转发到后端的 Pod（维护 iptables/ipvs 规则）。

**【为什么需要它】**
这是 K8s 能自动化调度、自愈的内部分工。理解它，排障时才知道"该看哪个组件的日志"。

**【在我们项目里怎么用】**
单节点，所有组件都在这一台 ECS 上。Sealos 帮我们把这些都装好并配好了。排障时如果 Pod 起不来，我们会看 kubelet 相关信息和 `kubectl describe`。

**【面试怎么答】**
> "控制面有 etcd 存集群状态、apiserver 是唯一入口、scheduler 决定 Pod 调度到哪、controller-manager 跑各种控制器保证期望状态。节点上有 kubelet 负责真正拉起 Pod 并汇报，kube-proxy 负责 Service 的网络转发。所有组件之间都通过 apiserver 通信，不直接对话。"

### 2.7 Calico / CNI

**【是什么】**
- **CNI（Container Network Interface，容器网络接口）**：一套"**给 Pod 联网的标准接口**"。K8s 自己不管具体怎么联网，而是定义一个接口，让第三方网络插件来实现。
- **Calico**：一个具体的 CNI 网络插件，负责给每个 Pod 分配 IP、让不同节点上的 Pod 能互相通信、还能做网络策略（防火墙规则）。

**【为什么需要 CNI】**
K8s 里成百上千个 Pod 需要每个都有 IP、还要能互相通、能跨节点通。这事很复杂，K8s 就把它交给专门的网络插件来做（谁装谁选）。**没装 CNI，Pod 会一直起不来（NotReady），因为它拿不到网络。**

**【在我们项目里怎么用】**
Sealos 装 K8s 时带了 **Calico** 作为网络插件。我们踩过一个坑——"**Calico CRD 时序问题**"：Calico 的一些自定义资源（CRD）要先就绪，相关组件才能正常起来，安装顺序/时机没对好会报错，等它就绪后就正常了。

**【面试怎么答】**
> "CNI 是给 Pod 联网的标准接口，K8s 自己不实现网络，交给插件。我项目里用的是 Calico，负责给 Pod 分 IP、跨节点通信和网络策略。没有 CNI 的话 Pod 会一直 NotReady 起不来。"

### 2.8 Sealos

**【是什么】**
Sealos 是一个"**一键安装 K8s 集群的工具**"，一条命令就能把 K8s 和网络插件都装好。它对标的是官方的 **kubeadm**（官方装 K8s 的标准工具，但步骤更多更繁琐）。

**【为什么需要它】**
手动用 kubeadm 装 K8s 步骤多、容易出错（初始化、装网络插件、配证书……）。Sealos 把这些打包成一键操作，对新手和快速搭建非常友好。

**【在我们项目里怎么用】**
我们就是用 Sealos 一键装的单节点 K8s v1.31.9 + Calico。

**【面试怎么答】**
> "Sealos 是一键装 K8s 的工具，对标 kubeadm 但更省事，一条命令把集群和网络插件都装好。我项目里就是用它装的单节点 K8s v1.31.9。如果面试官更看重原理，我也了解 kubeadm 的手动流程：初始化控制面、装 CNI、加入节点。"

### 2.9 污点 Taint 与容忍 Toleration

**【是什么】**
- **污点（Taint）**：打在**节点**上的一个"**别在我这跑**"的标记。就像给一张桌子贴"这里有人预定，别坐"。
- **容忍（Toleration）**：打在**Pod**上的一个"**我不介意那个标记**"的声明。就像客人说"我知道有预定，但我有特权可以坐"。

只有 Pod 的"容忍"能匹配上节点的"污点"，这个 Pod 才允许被调度到那个节点。

**【为什么需要它 / 单节点为什么要去污点】**
K8s 默认会给**控制面节点（master）打一个污点**，意思是"我是管理节点，普通业务 Pod 别来我这跑，我只干管理的活"。这在多节点集群里是对的（保护 master）。

但我们是**单节点**——整个集群就这一台机器，它既是 master 又得跑业务 Pod。如果不处理，master 上的污点会让我们的应用 Pod 一直调度不上去（Pending）。所以要**去掉（或让 Pod 容忍）这个污点**，业务 Pod 才能在这唯一的节点上跑起来。

**【在我们项目里怎么用】**
单节点部署时，去掉了 control-plane 节点的污点，让应用 Pod 能正常调度到本节点。

**【面试怎么答】**
> "污点是打在节点上的排斥标记，容忍是打在 Pod 上的'我不介意'。K8s 默认给 master 打污点不让业务 Pod 上去。我是单节点，只有这一台机器，所以必须去掉 master 的污点，否则应用 Pod 会一直 Pending 调度不上去。"

### 2.10 存储：PV / PVC / StorageClass / 动态供给 / NFS 制备器

**【是什么】**（用"租房"来理解，超好记）
- **PV（PersistentVolume，持久卷）**：一块**实际的存储空间**（比如一块硬盘/一个 NFS 目录）。相当于"**一套实际存在的房子**"。
- **PVC（PersistentVolumeClaim，持久卷声明）**：Pod 提出的"**我要一块多大的存储**"的申请。相当于"**租房需求单：我要一间 10 平的房**"。
- **绑定**：K8s 把合适的 PV 分配给 PVC，Pod 就用上了。相当于"中介把合适的房子租给你"。
- **StorageClass（存储类）**：一个"**自动建房的模板/中介**"。有了它，不用人工提前准备 PV，PVC 一申请，它就**自动创建对应的 PV**。
- **动态供给（Dynamic Provisioning）**：就是靠 StorageClass 实现的"**申请即自动创建存储**"，不用运维手动一个个建 PV。
- **NFS 制备器（nfs-subdir-external-provisioner）**：一个具体的"自动建房工人"，它对接 NFS（网络文件共享），PVC 一来就自动在 NFS 上建一个子目录当作存储给 Pod 用。

**【为什么需要它】**
容器/Pod 是"用完就没"的（重建后里面的数据丢了）。但有些数据要持久保存（比如 Harbor 存的镜像、数据库数据）。所以需要把数据存到 Pod 外面的持久存储上。手动建 PV 太麻烦，就用 StorageClass 做动态供给自动化。

**【在我们项目里怎么用】**
我们装了 **nfs-subdir-external-provisioner + StorageClass**，实现 NFS 动态存储。这样像 Harbor 这种需要持久化数据的组件，一申请 PVC 就自动在 NFS 上分配存储，不用手动建 PV。

**【面试怎么答】**
> "用租房比喻：PV 是实际的房子，PVC 是租房申请，StorageClass 是能自动建房的中介，实现动态供给——PVC 一申请就自动创建 PV，不用手动建。我项目里用 nfs-subdir-external-provisioner 加 StorageClass 做 NFS 动态存储，给 Harbor 这类要持久化的组件用。"

### 2.11 Service 与服务发现

**【是什么】**
- **Service**：给一组 Pod 提供一个**固定的访问入口**（固定虚拟 IP + 固定 DNS 名字）。
- **ClusterIP**：Service 最常见的类型，只在**集群内部**可访问的固定 IP。
- **Service DNS**：K8s 内置 DNS，会给每个 Service 分配一个**域名**，格式像 `服务名.命名空间.svc.cluster.local`。集群内的 Pod 直接用这个名字就能访问到对应服务。

**【为什么需要它 / 为什么 Pod 间用 Service 名而非 IP】**
Pod 是"临时的"——会挂、会被重建、重建后 **IP 会变**。如果 A 直接记着 B 的 Pod IP，B 一重建 A 就找不到它了。**Service 提供一个永远不变的名字和 IP**，背后的 Pod 换来换去都没关系，Service 会自动把流量转发到当前活着的 Pod 上。所以集群内互相调用一律用 Service 名字（DNS），不用 Pod IP。

**【在我们项目里怎么用】**
这里有个我们**真实踩过并解决的关键点**：ArgoCD 要访问 Gitea 拉代码时，**必须用 Gitea 的集群内 Service DNS 名字来访问**，而不是外部地址或 Pod IP——因为它们都在同一个集群里，用 Service DNS 才稳定、才通。

**【面试怎么答】**
> "Pod 的 IP 会变，所以集群内互相访问不能记 Pod IP，要用 Service。Service 提供固定 IP 和 DNS 名字，背后 Pod 换了也不影响。我项目里 ArgoCD 访问 Gitea 拉代码，就是用 Gitea 的集群内 Service DNS 名字，这样才稳定可达。"

---

### 2.12 Ingress 与 Ingress Controller

**【是什么】**
- **Ingress**：一份"**七层路由规则表**"（工作在 HTTP/HTTPS 层），写着"访问 a.com 转到 A 服务，访问 b.com 转到 B 服务，/api 路径转到后端"。它本身只是**规则**。
- **Ingress Controller**：**真正执行这些规则的程序**（我们用的是 Ingress-nginx，本质是个 nginx）。它读取 Ingress 规则，按规则把外部请求转发到对应的 Service。

**【为什么需要它 / 和 Service 的区别】**
- Service（ClusterIP）默认只在集群内部能访问，外面进不来。要让外部用户通过域名访问，就需要一个统一的"大门 + 按域名/路径分流"的东西——这就是 Ingress。
- **区别**：Service 是"给一组 Pod 一个内部固定入口（四层，基于 IP/端口）"；Ingress 是"集群统一对外大门，按域名/路径做七层 HTTP 分发"。多个服务可以共用一个 Ingress 入口，按 host 分发到不同 Service。

**【在我们项目里怎么用】**（含一个重要坑）
我们用 **Ingress-nginx** 对外暴露网页应用。有个特殊处理：**因为服务器没做 ICP 备案，阿里云会拦截 80/443 端口的域名访问**，所以我们让 Ingress-nginx 占用宿主机的 **9443 端口**（避开 80/443），再通过**本地 SSH 隧道**把远程 9443 映射到本地来访问，从而绕过备案限制、也能正常验证效果。

**【面试怎么答】**
> "Service 是给一组 Pod 的内部固定入口（四层），Ingress 是集群统一对外大门，按域名和路径做七层 HTTP 分发，多个服务能共用一个入口。真正干活的是 Ingress Controller，我用的是 Ingress-nginx。我这台机器没备案，80/443 被拦，所以让 Ingress 走 9443 端口，再用 SSH 隧道从本地访问。"

### 2.13 Harbor（私有镜像仓库）

**【是什么】**
Harbor 是一个**自建的私有镜像仓库**（企业版的"镜像网盘"）。除了存镜像，还带网页管理界面、用户权限、镜像扫描、版本管理等功能。

**【为什么需要它】**
- 公司的镜像不能随便传到公网的 Docker Hub（涉密、也慢）。私有仓库放在自己内网，安全、快。
- 需要权限控制（谁能推、谁能拉）、镜像分项目管理。
- CI/CD 流水线需要一个稳定的地方存构建好的镜像，供 K8s 拉取。

**【在我们项目里怎么用】**
我们用 **Helm** 装了 Harbor（见 2.17）。流水线里：`nerdctl build` 构建好镜像后 **推送到 Harbor**，K8s 部署时再从 Harbor **拉取**这个镜像。Harbor 的数据用前面的 NFS 动态存储做持久化。

**【面试怎么答】**
> "Harbor 是自建私有镜像仓库，相当于企业内部的镜像网盘，带权限管理、Web 界面、镜像扫描。公司镜像不方便放公网、也要权限控制，所以自建。我项目里构建好的镜像推到 Harbor，K8s 再从 Harbor 拉镜像部署。"

### 2.14 Gitea（代码仓库）

**【是什么】**
Gitea 是一个**轻量级的自建 Git 代码托管平台**，功能类似 GitHub/GitLab 的核心部分（存代码、看提交、开 issue、PR），但**非常轻、省资源**，用 Go 写的。

**【为什么需要它 / 和 GitLab 的取舍】**
- 需要一个自己的 Git 仓库来存代码和部署清单（YAML），作为 GitOps 的"唯一真相源"。
- **为什么选 Gitea 不选 GitLab**：GitLab 功能全但**极其吃资源**（内存要好几个 G，单节点小机器扁不住）；Gitea 极轻量，几百 M 就能跑，非常适合我们这种单节点最小可用版。取舍就是"够用就好、省资源优先"。

**【在我们项目里怎么用】**（含一个坑）
Gitea 存我们的代码（index.html、Dockerfile、deploy/ 目录下的 YAML）。ArgoCD 就盯着 Gitea 里的这个仓库。踩过的坑：**Gitea 默认禁止用 root 账号操作/推送**（安全设计），要用普通用户。

**【面试怎么答】**
> "Gitea 是轻量的自建 Git 平台，功能类似 GitLab 但省资源。我单节点机器资源有限，GitLab 太吃内存，所以选 Gitea。它存我的代码和部署 YAML，作为 GitOps 的唯一真相源，ArgoCD 就盯着它。"

### 2.15 Jenkins（CI 工具）

**【是什么】**
Jenkins 是最经典的**CI/CD 自动化工具**，说白了是一个"**自动化任务执行器**"：你把"拉代码→测试→构建镜像→推仓库"这些步骤写成一个**流水线（Pipeline）**，它就能自动按顺序执行。

关键概念：
- **CI（持续集成）**：前面说过，"代码→构建→镜像"这一段的自动化。
- **Pipeline（流水线）**：把一连串步骤（stage）串起来自动执行，比如：拉代码 → 编译 → 单元测试 → 构建镜像 → 推 Harbor。
- **Jenkinsfile**：用代码（文本文件）描述这条流水线，放进 Git 仓库里管理（Pipeline as Code）。这样流水线本身也能版本化、可追溯。

**【为什么需要它】**
没有它，每次改代码都要手动构建、手动推镜像，又慢又容易出错。Jenkins 让这一切自动化，一提交代码就自动跑完整条 CI 流程。

**【在我们项目里怎么用】**（如实说明）
我们**装好了 Jenkins**，但 **CI 的自动化还没完全接入**——目前构建镜像、推 Harbor 这段还是手动用 nerdctl 做的。所以面试时要诚实：CD（ArgoCD）是全自动跑通的，CI（Jenkins 自动化）是装好了但还在规划完善中。踩过的坑：**离线环境装 Jenkins 时插件装不上，跳过了默认插件安装**。

**【面试怎么答】**
> "Jenkins 是 CI/CD 自动化执行器，把拉代码、构建、测试、推镜像写成 Pipeline 自动跑，用 Jenkinsfile 把流水线代码化。我项目里 Jenkins 装好了，但 CI 自动化还没完全接入，目前构建推镜像是手动的，这块是我下一步要完善的。CD 那边我用 ArgoCD 已经全自动跑通了。"

### 2.16 ArgoCD 与 GitOps

**【是什么】**
- **GitOps**：一种运维思想——**把 Git 仓库当作系统"唯一真相源（Single Source of Truth）"**。你想让线上变成什么样，就去改 Git 里的 YAML；有个工具盯着 Git，发现和线上不一致就自动把线上改成 Git 里的样子。**"改 Git = 改线上"。**
- **ArgoCD**：实现 GitOps 的工具。它**持续盯着 Git 仓库**，把 Git 里声明的"期望状态"和 K8s 里的"实际状态"作对比，不一致就**自动同步（Sync）**过去。

GitOps 四大好处（面试爱问）：
- **声明式**：Git 里全是描述"想要什么"的 YAML。
- **Git 为唯一真相源**：想改线上必须改 Git，所有变更都有记录、可审计。
- **自动同步 + 自愈**：线上被人手动改乱了，ArgoCD 发现和 Git 不符，会自动改回来（自愈）。
- **回滚简单**：想回退版本，`git revert` 回退到上一个提交，ArgoCD 自动把线上也退回去。

**【为什么需要它】**
传统部署是"人手动敲 kubectl apply"，容易出错、没记录、难回滚、线上被人偷偷改了也不知道。GitOps 用 Git 管一切，安全、可追溯、能自愈、好回滚。

**【在我们项目里怎么用】**（这是我们跑通的核心，含坑）
ArgoCD 盯着 Gitea 里的仓库。我们**改了 deploy/deployment.yaml 里的镜像 tag（比如 v1→v2）并 git push 后，ArgoCD 自动检测到变化，把新版本同步部署到 K8s，浏览器就看到更新了**——这条 GitOps 链路是完整跑通的。踩过的坑：① ArgoCD 连 Gitea 时要**协议匹配（HTTP/HTTPS 别配错）**；② ArgoCD 访问 Gitea 要用**集群内 Service DNS 名字**（见 2.11）。

**【面试怎么答】**
> "GitOps 就是把 Git 当唯一真相源，想改线上就改 Git 里的 YAML，工具自动把线上同步成 Git 描述的样子。我用 ArgoCD 实现：它盯着 Gitea 仓库，我改了 deployment 的镜像 tag 并 push，它自动检测并同步部署到 K8s。好处是有记录、能自愈、回滚就是 git revert。这是我项目里完整跑通的 CD 环节。"

### 2.17 Helm（K8s 包管理器）

**【是什么】**
Helm 是 **K8s 的包管理器**，相当于 Linux 里的 yum/apt、手机上的应用商店。它把一个复杂应用的一堆 YAML 打包成一个**Chart（图表/安装包）**，一条 `helm install` 就能装好。

关键概念：
- **Chart**：一个应用的安装包模板，里面是参数化的 YAML（可以传参定制，比如设置密码、存储大小）。

**【为什么需要它 / 为什么用它装 Harbor】**
像 Harbor 这种应用，背后有一大堆组件（数据库、Redis、核心服务、镜像存储……），手写几十个 YAML 又累又易错。用 Helm，官方提供了 Harbor 的 Chart，**一条命令加几个参数就装好整套**，还方便升级和卸载。所以我们装 Harbor 就是用 Helm。

**【面试怎么答】**
> "Helm 是 K8s 的包管理器，像 yum/应用商店，把一堆 YAML 打包成 Chart，一条命令装好复杂应用还能传参定制。我装 Harbor 就是用 Helm，因为 Harbor 组件多，手写 YAML 太麻烦，用官方 Chart 一键装。"

### 2.18 buildkit / 镜像构建方式

**【是什么】**
- **docker build**：传统的镜像构建方式，靠 Docker 守护进程来构建。
- **buildkit**：新一代的镜像构建引擎，**更快（能并行构建层）、缓存更好、更安全**，现在 Docker 新版本底层也用它。可以独立于 Docker 使用。
- **kaniko**：一个能**在容器/K8s 集群内部构建镜像**的工具，**不需要 Docker 守护进程、不需要特权**。适合在 K8s 里做 CI（因为在容器里跑 docker build 需要特权、不安全）。

**【为什么需要它 / 三者对比】**
- 传统 `docker build` 需要 Docker 守护进程，在 K8s 里做 CI 时不方便、不安全。
- **buildkit** 更快更现代，是当前主流构建引擎。
- **kaniko** 是为"在 K8s 集群里安全地构建镜像"而生的，是未来把 CI 完全搬进 K8s 的方案。

**【在我们项目里怎么用】**（含坑）
我们用 **buildkit** 作为构建引擎，配合 nerdctl 构建镜像。踩过的坑：**buildkit 有自己独立的镜像加速配置**，要单独配（和 containerd、docker 的配置分开，见 2.4）。kaniko 我们还没上，是规划中"把 CI 搬进 K8s"的下一步。

**【面试怎么答】**
> "docker build 靠 Docker 守护进程，buildkit 是更快更现代的构建引擎、能并行和更好缓存，kaniko 能在 K8s 容器内不用特权就构建镜像、适合集群内 CI。我项目里用 buildkit 配 nerdctl 构建，踩过 buildkit 镜像加速要单独配的坑。kaniko 是我规划中把 CI 完全搬进 K8s 的方案。"

## 三、完整流水线数据流精讲（v1→v2 那次更新）

> 目标：能对着这条链路完整复述一遍。面试官说"讲讲你那个项目的流水线"，你就把下面八步讲出来。

场景：网页上的一句标题要从 v1 改成 v2，看这一个改动怎么自动上线。

**第 1 步：改代码。**
在本地把 `index.html` 的标题从 v1 改成 v2。这是开发行为，改的是“图纸”。项目目录里有：`index.html`、`Dockerfile`（`FROM nginx:alpine`，把网页拷进 nginx 镜像）、`deploy/` 目录（deployment.yaml / service.yaml / ingress.yaml）。

**第 2 步：构建镜像（nerdctl build + buildkit）。**
用 `nerdctl build` 把代码和 Dockerfile 打包成一个新镜像，打上新标签，比如 `harbor地址/项目/应用:v2`。底层是 buildkit 在干活。“图纸”在这一步变成了“标准集装箱”。

**第 3 步：推送镜像到 Harbor。**
`nerdctl push harbor地址/项目/应用:v2`，把新镜像传到私有仓库 Harbor 里存着。“集装箱”进了“成品仓库”，等着发货。

**第 4 步：改部署清单的镜像 tag。**
把 `deploy/deployment.yaml` 里的镜像字段从 `:v1` 改成 `:v2`。这就是改“发货单”——告诉系统“这次要上 v2 版本的货”。注意：这里只是改一份描述文件，并没有直接去 K8s 上手动部署。

**第 5 步：git push 到 Gitea。**
把改动（代码 + deployment.yaml）提交并 push 到 Gitea 仓库。现在 Git 里的“期望状态”已经是 v2 了，而线上还是 v1——两者出现了差异。

**第 6 步：ArgoCD 自动检测到差异。**
ArgoCD 一直盯着 Gitea 仓库。它发现 Git 里写的是 v2、集群里跑的是 v1，状态变成 OutOfSync（不一致）。（ArgoCD 访问 Gitea 用的是集群内 Service DNS 名字。）

**第 7 步：ArgoCD 同步部署到 K8s。**
ArgoCD 把 Git 里的新 deployment.yaml 应用到集群。K8s 的 Deployment 发现镜像 tag 变了，就做**滚动更新**：先拉新镜像 v2（从 Harbor）→启一个新 Pod→新 Pod 就绪后再终止旧 Pod，保证服务不中断。

**第 8 步：浏览器看到更新。**
通过 SSH 隧道访问 Ingress-nginx（9443 端口），请求进来后 Ingress 按规则转给 Service，Service 再转给背后的 v2 Pod，页面显示变成 v2。完成！

**一句话总结（面试能背）：**
> "我改 index.html → nerdctl build 构建 v2 镜像 → 推到 Harbor → 改 deployment.yaml 的镜像 tag 为 v2 → git push 到 Gitea → ArgoCD 检测到 Git 和集群不一致，自动同步 → K8s 滚动更新拉 v2 镜像起新 Pod → 通过 Ingress 访问，浏览器看到 v2。整条链路里我只做了两个动作：构建推镜像、改 tag 并 push，剩下的部署全是 ArgoCD 自动完成的。"

### 为什么这么设计（面试追问时的亮点）
- 为什么用镜像 tag 区分版本而不是都用 latest？——用固定 tag（v1/v2）才能明确知道线上跑的是哪个版本、才能回滚；latest 会让你搞不清到底是哪个版本。
- 为什么不直接 kubectl apply，而要绕 Git + ArgoCD？——因为 GitOps 有记录、能自愈、回滚只需 git revert，比手动 apply 安全可控。

## 四、排障思维与踩坑复盘（面试最加分的部分）

> 面试官最想听的不是“你会多少命令”，而是“遇到问题你怎么想、怎么一步步定位的”。下面把真实踩过的坑归成几类方法论。

### 4.1 网络类（源被墙 / 镜像失效 / 备案拦截）

**我们踩过的坑**：Docker 官方源被墙（换阿里云源）、镜像加速地址失效（换新地址）、ICP 备案拦截 80/443（用 SSH 隧道绕过）。

**思维链：现象 → 怎么想 → 怎么查 → 怎么解决**
- 现象：拉镜像、装软件超时，或域名访问不了。
- 怎么想：先分清到底是哪种问题——是“网络不通”、“地址写错”还是“被拦截”？三者处理方式完全不同。
- 怎么查（分段定位法，核心技巧）：
  1. 先用 `curl` 测内网/本机服务（如 `curl 127.0.0.1:端口`），能通 → 说明服务本身没问题，问题在外部链路（备案/防火墙）。
  2. 再 `curl` 目标外部地址：连不上→可能网络不通或被墙；能连但报 404/名字解析错→地址写错；能连但被重定向到备案提示页→被备案拦截。
  3. 换个已知能通的地址（如国内镜像源）对比，能通就说明是原地址的问题。
- 怎么解决：源被墙→换国内源；加速失效→换新加速地址；备案拦截→避开 80/443、用 9443 + SSH 隧道。

### 4.2 端口冲突类

**我们踩过的坑**：Ingress 要占的端口被占用、组件启不来。

**思维链：**
- 现象：Pod 反复重启、服务启动失败。
- 怎么想：是不是“端口被别人占了”或“配置错”。
- 怎么查：① `kubectl logs <pod>`，如果 Pod 已经重启过，看上一个已死容器的日志用 `kubectl logs <pod> --previous`（这个很重要，当前容器可能日志是空的）；② `ss -lntp`（或 `ss -tulnp`）看哪个端口被谁占了。
- 怎么解决：换个端口（我们就是把 Ingress 改到 9443），或停掉占用端口的进程。

### 4.3 组件协议 / 配置类

**我们踩过的坑**：ArgoCD 连 Gitea 的 HTTP/HTTPS 协议不匹配、Gitea 禁止 root 用户、组件命名空间不对、ArgoCD 要用集群内 Service DNS。

**思维链：**
- 现象：组件 A 连不上组件 B，报认证/协议/连接错。
- 怎么想：三个维度逐个对——协议对不对（http 还是 https）、身份对不对（用户/权限）、地址对不对（用对命名空间、用 Service DNS 还是外部地址）。
- 怎么查：看报错关键词——写着 x509/tls 就是协议/证书；写着 401/403 就是权限；写着 no such host/解析失败就是地址/DNS。
- 怎么解决：协议改对、换普通用户、把地址改成集群内 Service DNS。

### 4.4 长任务保活（tmux/nohup 与 SIGHUP）

**我们踩过的坑**：SSH 一断开，正在跑的安装/下载进程就被杀了。

**原理：** SSH 断开时，系统会给该会话的进程发一个 **SIGHUP（挂断信号）**，默认会把前台进程一起干掉。
**解决：** 用 **tmux**（或 screen）开个会话再跑长任务，SSH 断了会话还在，重新连上 `tmux attach` 就能回来；或用 `nohup 命令 &` 让进程忽略 SIGHUP。我们用的是 **tmux**。

### 4.5 可复用的排障口诀
- **分段定位**：从里到外，先 curl 本机、再 curl 目标，看断在哪一段。
- **看日志优先**：`kubectl describe` 看事件，`kubectl logs`（必要时加 `--previous`）看容器日志。
- **三问法**：网络通不通？地址对不对？权限/协议对不对？
- **改一步验一步**：一次只改一个变量，改完验证，避免一次改很多搞不清是哪个生效。

## 五、面试高频问答（20 题以上）

> 用法：先遮住参考答案，自己先试着口说一遍，再对。答案都是口语化的，背不如理解后用自己话说。

**Q1. 讲讲你这个云原生项目 / 整体架构？**
> “我在一台阿里云 ECS（4核16G、Rocky Linux、单节点）上搭了一套云原生 DevOps 最小可用版。用 Sealos 装了单节点 K8s，底层 containerd，网络用 Calico，存储用 NFS 动态供给。代码放 Gitea，镜像存自建的 Harbor，用 nerdctl+buildkit 构建镜像，用 ArgoCD 做 GitOps 持续部署。整条链路是：改代码→构建推 Harbor→改部署 YAML 的 tag→push 到 Gitea→ArgoCD 自动同步到 K8s→通过 Ingress 访问。它是单节点的学习验证版，CD 已经全自动跑通，CI（Jenkins）装了但还在完善。”

**Q2. CI 和 CD 的区别？**
> “CI 是持续集成，管从代码到镜像这一段：构建、测试、打包推仓库。CD 是持续交付/部署，管从镜像到线上运行这一段。简单说，CI 把代码变成镜像，CD 把镜像变成线上服务。”

**Q3. K8s 为什么不用 Docker 了？**
> “不是不能用 Docker 镜像，镜像标准是通用的。是 K8s 不再通过 dockershim 调 Docker 了。因为 Docker 是大而全的全家桶，K8s 只需要符合 CRI 标准的核心运行时，所以从 1.24 移除了 dockershim，直接用 containerd 更轻量。我项目里就是 containerd + nerdctl。”

**Q4. Pod 一直 Pending 怎么排查？**
> “Pending 是调度不上去。我会 `kubectl describe pod` 看事件：常见原因是节点资源不够、有污点没容忍、没有可用的 PV（PVC 绑不上）。我单节点就遇过 master 污点导致 Pending，去掉污点就好了。”

**Q5. CrashLoopBackOff 怎么排查？**
> “这是容器能启但反复崩溃重启。我会 `kubectl logs <pod> --previous` 看上一次崩溃的日志（当前容器日志往往是空的），一般是应用配置错、端口冲突、依赖的服务连不上。找到报错再对症下药。”

**Q6. ImagePullBackOff 怎么排查？**
> “这是拉不到镜像。我会 `kubectl describe pod` 看具体报错：是镜像名/tag 写错、仓库需要登录没配 secret、还是网络拉不到。对应解决：改对 tag、配镜像仓库的 imagePullSecret、或配镜像加速。我项目里就因为加速地址失效踩过拉不到镜像的坑。”

**Q7. 镜像拉不下来怎么办？**
> “先分清是网络、地址还是权限问题。国内拉官方镜像慢就配镜像加速（注意 containerd、buildkit、docker 要分开配）；拉私有仓库报未授权就配登录 secret；tag 写错就改对。我还遇过加速地址失效，换个新的就好。”

**Q8. 什么是 GitOps？**
> “GitOps 就是把 Git 仓库当成系统的唯一真相源，所有想要的线上状态都写在 Git 里。想改线上就改 Git，工具自动把线上同步成 Git 描述的样子。好处是：所有变更有记录可审计、能自愈、回滚只需 git revert。”

**Q9. ArgoCD 怎么工作的？**
> “ArgoCD 持续盯着 Git 仓库，把 Git 里的期望状态和 K8s 的实际状态对比，不一致就自动同步。我项目里改了 deployment 的镜像 tag 并 push 到 Gitea，ArgoCD 自动检测到并同步部署，浏览器就看到新版本。”

**Q10. PVC 和 PV 的关系？存储怎么动态供给？**
> “PV 是实际的存储，像一套房子；PVC 是申请，像租房需求单。K8s 把合适的 PV 绑定给 PVC。动态供给是靠 StorageClass——PVC 一申请就自动创建 PV，不用手动建。我项目里用 NFS 制备器加 StorageClass 做动态存储，给 Harbor 用。”

**Q11. Service 和 Ingress 的区别？**
> “Service 是给一组 Pod 一个集群内部的固定入口，工作在四层（IP/端口）；Ingress 是集群统一对外的大门，工作在七层（HTTP），按域名和路径把外部请求分发到不同 Service。真正执行 Ingress 规则的是 Ingress Controller，我用的是 Ingress-nginx。”

**Q12. 污点和容忍是什么？**
> “污点是打在节点上的排斥标记，容忍是打在 Pod 上表示我不介意那个标记。只有 Pod 容忍能匹配节点污点，才能调度上去。K8s 默认给 master 打污点不让业务 Pod 上，我是单节点所以去掉了。”

**Q13. 为什么用单节点？生产环境应该怎么做？**
> “单节点是因为这是学习验证项目，成本可控、专注把整条 DevOps 链路跑通。生产环境不能单节点（挂了就全挂），应该多节点：控制面至少 3 个保证 etcd 高可用，工作节点多台、业务多副本分布在不同节点，这些是我后续想扩展的。”

**Q14. Deployment 如何滚动更新和回滚？**
> “改 Deployment 的镜像版本后，它会滚动更新：逐步启新 Pod、新的就绪再停旧的，保证不中断。回滚用 `kubectl rollout undo` 就能退到上个版本。我项目里因为是 GitOps，回滚更简单，直接 git revert 那个提交，ArgoCD 自动把线上也退回去。”

**Q15. 命名空间（Namespace）的作用？**
> “把集群分成几个逻辑房间，隔离不同项目/环境，方便管理权限和资源配额。我项目里 harbor、argocd、应用各在自己的命名空间，互不干扰。”

**Q16. 容器和虚拟机的区别？**
> “虚拟机是连操作系统都虚拟一套，重、启动慢；容器是共用宿主机内核，只打包应用和依赖，轻、秒启。类比：虚拟机是每家盖一栋房，容器是一栋楼里分出很多套房共用地基。”

**Q17. 描述一下 K8s 的核心组件？**
> “控制面有 etcd 存状态、apiserver 是唯一入口、scheduler 决定调度、controller-manager 保证期望状态；节点上 kubelet 拉起 Pod 并汇报，kube-proxy 管 Service 网络转发。所有组件都通过 apiserver 通信。”

**Q18. 声明式和命令式的区别？**
> “命令式是我一步步告诉系统怎么做；声明式是我只描述最终想要什么样，系统自己想办法达成。K8s 是声明式的，我写 YAML 描述期望，控制器不停把实际状态往期望纠。声明式能存进 Git、可重复，是 GitOps 的基础。”

**Q19. Harbor 为什么要自建？和 Docker Hub 区别？**
> “Docker Hub 是公网公共仓库，公司镜像不方便传上去、国内拉取也慢。Harbor 是自建私有仓库，放内网、安全快，还能做权限控制、镜像扫描、分项目管理。”

**Q20. Gitea 为什么不用 GitLab？**
> “GitLab 功能全但很吃内存，单节点小机器扁不住；Gitea 极轻量、功能够用。我是最小可用版，所以选省资源的 Gitea。”

**Q21. Sealos 和 kubeadm 的区别？**
> “都是装 K8s 的工具。kubeadm 是官方标准工具但步骤多；Sealos 把集群和网络插件打包成一键安装，更适合快速搭建。我用的是 Sealos。”

**Q22. CNI 是什么？为什么需要？**
> “CNI 是给 Pod 联网的标准接口，K8s 自己不实现网络，交给 Calico 这样的插件。没有 CNI，Pod 拿不到 IP、会一直 NotReady。”

**Q23. tmux 解决什么问题？**
> “SSH 断开时会给进程发 SIGHUP 把它杀掉，长时间的安装任务就中断了。我用 tmux 开会话跑，SSH 断了会话还在，重连 attach 回来就行。”

## 七、这个项目怎么写进简历、怎么在面试开口讲

### 7.1 简历项目描述（直接可用的最终版）

**项目名称：** 基于 Kubernetes 的云原生 DevOps 持续部署（GitOps）实践

**项目描述：**
> 在一台阿里云 ECS（4核16G、Rocky Linux、单节点）上独立搭建一套云原生 DevOps 环境，打通从代码提交到自动部署上线的完整链路。以 Kubernetes 为核心，自建代码仓库（Gitea）、私有镜像仓库（Harbor），使用 ArgoCD 实现 GitOps 声明式持续部署，实现了“改代码 → 构建镜像 → 推仓库 → Git 提交 → 自动同步部署”的自动化流程。

**主要职责 / 工作内容：**
- 负责阿里云 ECS 的采购选型与系统初始化（防火墙、SELinux、时间同步、国内软件源/镜像加速配置），基于成本考虑采用按量付费。
- 使用 Sealos 部署单节点 Kubernetes（containerd 运行时 + Calico 网络插件），并处理单节点去污点、Calico 初始化等集群可用性问题。
- 基于 NFS 搭建动态存储（nfs-subdir-external-provisioner + StorageClass），为 Harbor 等组件提供持久化存储。
- 使用 Helm 部署 Harbor 私有镜像仓库、部署 Gitea 代码仓库，并通过 Ingress-nginx 对外暴露服务。
- 使用 nerdctl + buildkit 构建应用镜像并推送至 Harbor，配置 ArgoCD 对接 Gitea 实现 GitOps 自动同步部署与回滚。
- 独立完成多类排障：镜像加速失效、端口冲突、组件协议与访问地址（集群内 Service DNS）、ICP 备案导致的端口限制等，积累了系统的排障思路。

> 提醒：简历里不写具体命令，只写“做了什么、用了什么、解决了什么”；命令细节留到面试聊天里自然展开。

### 7.2 2-3 分钟口头介绍话术模板

> 背的不是字，是“背景 → 做了什么 → 链路 → 难点/收获”这个结构。

> “我自己在一台阿里云服务器上搭了一套云原生 DevOps 的最小可用版，目的是把从开发改代码到自动部署上线这整条链路亲手跑通。
>
> 环境是一台 4核16G 的 ECS，单节点。我用 Sealos 装了 Kubernetes，底层是 containerd，网络用 Calico，存储用 NFS 做了动态供给。然后装了几个核心组件：代码放自建的 Gitea，镜像存自建的 Harbor，用 nerdctl 配 buildkit 构建镜像，最关键的是用 ArgoCD 做了 GitOps 持续部署。
>
> 整条链路是这样的：我改完代码，用 nerdctl 构建镜像推到 Harbor，再把部署 YAML 里的镜像 tag 改一下 push 到 Gitea；ArgoCD 一直盯着 Gitea，一发现变化就自动同步部署到 K8s，浏览器就能看到更新。回滚也很简单，git revert 一下就行。
>
> 过程中我踩了不少坑，比如国内拉镜像的加速配置、组件之间要用集群内 Service DNS 互访、服务器没备案 80/443 被拦我用 9443 加 SSH 隧道绕过，这些让我对排障思路有了比较真实的体会。
>
> 需要说明的是，它是单节点的学习验证版，CD 部分已经全自动跑通，CI（Jenkins）装好了但自动化还在完善中，多节点高可用和监控是我接下来想补的。”

### 7.3 诚信提醒（很重要）
- **只讲真做过、真理解的部分。** 单节点就实事求是说单节点，不要吹成生产高可用集群。
- **Jenkins CI 自动化没完全接入，就如实说“装了但还在完善”。** 面试官反而喜欢这种清楚知道自己做到哪、还差什么的人。
- **被问到没做过的东西，就说“这块我目前还没实践，但我知道思路是……”，把理解讲出来**，比乱编实现细节安全得多。

## 八、后续可增强项（面试被追问时的加分回答）

> 被问“这个项目还能怎么完善”时，把下面这些当“我规划中的下一步”来答，显得有全局规划。

- **Jenkins 完整 CI 自动化**：把“拉代码→构建→推镜像→改 tag”写成 Jenkinsfile 自动跑，并用 **kaniko 在 K8s 集群内构建镜像**（不需特权、更安全），真正做到 CI 也全自动。
- **监控告警**：接入 **Prometheus + Grafana** 做指标采集和可视化大盘，配告警规则，补上运维最核心的“看得见”能力。
- **多节点高可用**：把单节点扩成多节点，控制面多副本保证 etcd 高可用，业务 Pod 分布到不同节点，避免单点故障。
- **仓库升级**：资源充足时可用 **GitLab 替代 Gitea**，获得内置 CI、更完整的权限和审批流。
- **安全与证书**：给域名备案、上真实证书（如 cert-manager 自动签发），走正常 443，不再靠 SSH 隧道。
