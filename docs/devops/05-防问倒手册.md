## 使用方法与真实性标记体系

全文每个知识点都带真实性标记,面试时**只能按标记的口径讲,绝不越线**:

| 标记 | 含义 | 面试口径 |
|------|------|---------|
| 【实操】 | 你亲手执行过的操作 | 可以说"我做过",可以报命令和细节 |
| 【实测】 | 你亲手验证过结果的测试 | 可以报结果数据(如拦截ID、请求数、Bound) |
| 【原理】 | 学过概念、能讲清原理,但未在本项目实操 | 说"我理解原理是……没实际操作过" |
| 【规划】 | 你想过、能说出方案的下一步 | 说"我的规划是……还没实施" |
| 【未做】 | 完全没碰过 | 走统一话术:"没做过,但原理我知道,给我一周能上手" |

### 什么叫"不会被问到"——七层防御模型

面试官对项目的一切提问,都落在这七层里的某一层。**每个话题逐层自查,哪层答不上就补哪层**:

```
L1 是什么   —— 定义、一句话讲清
L2 为什么   —— 存在意义、为什么选它不选别的
L3 怎么做的 —— 你的真实操作、配置、命令
L4 坏了怎么排 —— 排障思路、你踩过的真实坑
L5 和谁比   —— 与替代方案对比、选型依据
L6 被质疑   —— "单节点能行?""你真会?""照抄教程吧?"
L7 延伸边界 —— 生产化怎么做、没做过的怎么办
```

**最终兜底话术**(七层之外的陌生问题,这是"不被问死"的最后一道防线):

> "这个我实际没有操作过,我不跟您吹。我的理解是它原理大概是……(讲你能讲的部分)。如果工作要用,我会先看官方文档,在测试环境搭一遍验证,给我一周左右可以上手。"

这句话在 8/25 面试那种压力面里已经验证过:诚实 + 原理 + 上手计划,比硬编安全一百倍。

## 1.2 三级项目介绍(全部真实,直接背)

### 30 秒版(电话/开场)

> 我这个项目是在阿里云一台 4 核 16G 的 ECS 上,用 Sealos 从零搭的单节点 K8s 集群,版本 1.31.9,围绕它把云原生 DevOps 流水线整个搭起来了:代码仓库 Gitea、镜像仓库 Harbor、持续集成 Jenkins、持续部署 ArgoCD,走 GitOps。我自己完整跑通过一次"改代码 → 构建镜像推 Harbor → 改 Git 里的部署清单 → ArgoCD 自动同步到 K8s 滚动更新"的闭环,CD 是全自动的,CI 目前半自动。过程踩了 containerd 冲突、镜像源失效、备案拦截等十几个坑,都是我自己看报错查文档解决的。

### 60 秒版(加数字和细节)

在 30 秒版基础上,补:

> 环境细节:Rocky Linux 10.2,按量付费一小时九毛三,带宽按流量。容器运行时用的是 containerd 而不是 Docker——因为装 Sealos 时跟之前装的 Docker 冲突了,我把 Docker 卸了,K8s 1.24 之后本来也不需要 Docker。存储用 NFS 加 StorageClass 做动态供给,我把 nfs-storage 设成了默认 StorageClass,提交 PVC 自动建 PV。入口用 Ingress-nginx,因为没备案被阿里云网关拦,我把入口改到 9443 非标端口,再用 SSH 隧道加 nip.io 泛解析域名访问,HTTP 流量封在 SSH 隧道里网关读不到 Host 头,就绕开了。

### 2 分钟版(被要求"详细讲讲"时)

在 60 秒版基础上,再补三块:

1. **企业化裁剪**:参考的教程原版是多地多中心架构,我按企业命名规范裁成了单数据中心版(BJ-DC01 / bj-az01),Harbor 用 chart 内置 PostgreSQL + Redis 不用外部的、关掉 trivy 扫描组件,数据库用 SQLite 的 Gitea 替代吃内存几个 G 的 GitLab——单机 16G 我把每个组件的内存都算过账,总共 9-10G,留了 6G 余量。

## 1.4 全链路数据流:8 步逐层拆解

每步都按"**谁干的 → 真实地址/命令 → 断了会怎样 → 追问链**"掌握。这条链是整个项目的灵魂,必须能脱稿讲。

### 第 1 步:提交代码到 Gitea【实操】

- 动作:本地写 `index.html` + `Dockerfile` + `deploy/` 目录(deployment/service/ingress 三份清单),git push 到 Gitea 的 `demo-app` 公开仓库(用 Gitea API 创建)。
- 地址:从本地走 `gitea.127.0.0.1.nip.io`(经 SSH 隧道);ArgoCD 从集群内走 `http://gitea.devops.svc.cluster.local:3000/gitea/demo-app.git`。
- 代码和部署清单放同一个仓库,`deploy/` 目录就是 ArgoCD 监听的 GitOps 清单目录。
- 断了会怎样:push 失败先看网络/认证;Gitea 挂了 ArgoCD 会一直拿不到最新清单,保持旧版本运行。

### 第 2 步:构建镜像(CI 核心动作,当前手动)【实操】

```bash
nerdctl build -t harbor.127.0.0.1.nip.io:9443/devops/demo:v2 . --insecure-registry
```

- 底层:`nerdctl build` 需要 **buildkit** 后端(最早报过 `buildctl not found`),buildkit 以 systemd service 跑,关键参数 `--containerd-worker-namespace=k8s.io`,让构建产物直接进 K8s 用的命名空间。
- 拉基础镜像(nginx:alpine)走 buildkit **自己的**加速配置 `/etc/buildkit/buildkitd.toml`(它不读 containerd 的加速)。
- 追问链:Dockerfile 怎么写的 → `FROM nginx:alpine` + `COPY index.html /usr/share/nginx/html/index.html` + `EXPOSE 80` + `CMD ["nginx","-g","daemon off;"]`;RUN 和 CMD 区别 → RUN 是构建时执行,CMD 是容器启动时的默认命令。

### 第 3 步:推送镜像到 Harbor【实操】

```bash
nerdctl push harbor.127.0.0.1.nip.io:9443/devops/demo:v2 --insecure-registry
```

- 前提三件套(缺一不可,都真实踩过):① `nerdctl login --insecure-registry ...` 登录;② containerd 的 `certs.d/harbor.127.0.0.1.nip.io:9443/hosts.toml` 显式信任 HTTP 仓库(`skip_verify = true`,**目录名必须带端口**);③ 项目在 Harbor 里建好(公开,免 imagePullSecret)。
- 真实验证:Harbor 界面里 `devops/nginx:v1` 和 `devops/demo:v1/v2`,大小 24.86MiB。
- 断了会怎样:报 `push access denied` / `authorization failed`——我真实踩过一次,原因不是密码错,是服务器访问自己的公网域名,流量出公网绕一圈被备案网关拦截,拿回来的是拦截 HTML 不是仓库响应;换成解析到 127.0.0.1 的域名就好了。【实测】

### 第 4 步:更新 GitOps 清单【实操】

```bash
sed -i 's/demo:v1/demo:v2/' deploy/deployment.yaml
git commit -m "update to v2" && git push
```

- 这是 GitOps 的核心:**改 Git = 改线上**。镜像 tag 的变更作为一次 Git 提交留痕,可追溯、可回滚。
- 追问:为什么改清单而不是直接 kubectl set image?→ 直接改集群是"命令式"的,ArgoCD 会检测到集群和 Git 不一致(selfHeal 开着会把它改回去);改 Git 才是声明式的正路。

### 第 5 步:ArgoCD 检测变化【实操】

- ArgoCD 默认**每 3 分钟轮询**一次 Git 仓库;演示时用 `kubectl -n argocd patch application demo-app` 加 refresh 注解催它立即同步。
- repoURL 必须用**集群内 Service DNS**(`gitea.devops.svc.cluster.local:3000`)——ArgoCD 跑在 Pod 里,解析不了 nip.io 的公网回环域名。【实操,高频追问】
- 断了会怎样:一直显示 OutOfSync 但不动作,先查 ArgoCD 能不能连到 repo(Pod 内 curl Service DNS)。

### 第 6-7 步:对比与自动同步【实操】

- ArgoCD 把 Git 里的声明和集群实际状态对比 → 界面显示 **OutOfSync** → `syncPolicy.automated` 触发自动 apply → 请求进 **API Server** → 状态写 **etcd** → **Deployment Controller** 创建新 ReplicaSet → **Scheduler** 选节点(单节点没得选)→ **kubelet** 调 containerd 从 Harbor 拉新镜像 → 新 Pod Running,旧 Pod 终止,滚动更新。
- `selfHeal: true` 的作用:有人手动改了集群资源,ArgoCD 会自动改回和 Git 一致。`syncOptions: CreateNamespace=true`:demo namespace 不存在就自动建。
- 界面证据:Synced + Healthy。【实测,有截图 06_ArgoCD界面】

### 第 8 步:用户访问验证【实操】

- 浏览器 `http://demo.127.0.0.1.nip.io:9443` → nip.io 解析成 127.0.0.1 → SSH 隧道送到服务器 9443 → **Ingress-nginx**(hostNetwork 占宿主机 9443)按 Host 头匹配 Ingress 规则 → 转发给 **Service**(ClusterIP,selector `app=demo` 匹配 Pod 标签,**靠标签不靠名字**)→ Pod → 页面显示 v2。
- 追问链:Service 怎么找到 Pod → selector 匹配 label,松耦合;为什么不用名字 → Pod 名和 IP 都会变,标签稳定。Ingress 和 Ingress-nginx 什么关系 → Ingress 是七层路由规则,Ingress-nginx 是执行规则的控制器,光有规则没控制器不生效。

## 1.5 v1→v2 完整实战还原(命令级,必须能默写)

```bash
# ① 改代码:index.html 里 v1 改成 v2(顺手补了 <meta charset="utf-8"> 修中文乱码)

# ② 构建新镜像(走 buildkit)
nerdctl build -t harbor.127.0.0.1.nip.io:9443/devops/demo:v2 . --insecure-registry

# ③ 推到 Harbor
nerdctl push harbor.127.0.0.1.nip.io:9443/devops/demo:v2 --insecure-registry

# ④ 改部署清单的镜像 tag
sed -i 's|demo:v1|demo:v2|' deploy/deployment.yaml

# ⑤ 提交清单变更(GitOps 真相源变更)
git add . && git commit -m "update to v2" && git push

# ⑥ 催 ArgoCD 立即同步(默认 3 分钟轮询,等不及就 patch refresh)
kubectl -n argocd patch application demo-app --type merge -p '{"metadata":{"annotations":{"argocd.argoproj.io/refresh":"normal"}}}'

# ⑦ ArgoCD 自动同步 → 滚动更新 → 浏览器 http://demo.127.0.0.1.nip.io:9443 看到 v2
```

**面试金句**:整个过程我没有手动 kubectl apply 部署、没有手动改集群任何资源——只改了代码和 Git 里的清单,"上线"动作全由 ArgoCD 完成。构建那步(CI)目前还是手动跑,"更新清单 → 部署到集群"这段(CD)已经全自动。这就是 GitOps:**以 Git 为唯一真相源,声明式地把集群状态同步到和 Git 一致**。

## 1.6 组件逐一深挖(12 个组件 × 七层防御)

> 每个组件按 L1~L7 过一遍。标注了【原理】【规划】【未做】的层,面试按对应口径讲。

### ① Sealos(L3 主角)

- L1:一键部署 K8s 集群的工具,对标 kubeadm,把整套集群和插件打包成镜像一条命令装好。【原理】
- L2 为什么用它:教程用它;kubeadm 要自己配证书、装组件,Sealos 全包了。
- L3 怎么做的:RPM 源装 5.1.1;`sealos run labring/kubernetes:v1.31.9 labring/helm:v4.0.1 labring/calico:v3.28.1 --masters 172.17.175.55`(单节点只写 --masters 不写 --nodes);它自动装 containerd、自动去掉 master 污点。【实操】
- L4 坑:报 `containerd is installed ... please uninstall it first`(见踩坑 #1);第一次跑 Calico 报 CRD 时序错,原样重跑第二次成功(Sealos 幂等,复用已下载镜像)。【实测】
- L5 对比:kubeadm(官方,步骤多、可控)/ Sealos(打包封装,快)/ minikube(本地学习,单机容器里跑)。
- L6 质疑:"Sealos 是不是把一切黑盒了?" → 答它本质还是拉起 kubeadm 那套组件,装完我逐一验证过 `kubectl get pod -A` 里 etcd/apiserver/scheduler/controller-manager 都在,组件我都能讲清分工。
- L7 延伸:多节点就是 `--masters IP1,IP2,IP3 --nodes IP4,IP5`。【原理/规划,未实操】

### ② K8s 控制面(L1/L2 高频)

- L1:五组件——**API Server**(唯一管理入口)、**etcd**(存所有状态)、**Controller Manager**(对比期望与实际、纠偏)、**Scheduler**(调度选节点)、**kubelet**(节点上真正拉起容器)。
- L2 关键区分(模拟面试失分点):提交 yaml 走 **API Server**,不是 Service;**Controller 在监控纠偏**,不能说"Deployment 在监控";用户访问走 **Service**(外网先过 Ingress)。
- L3:我集群里 `kubectl get pod -A` 能看到 etcd、kube-apiserver、kube-controller-manager、kube-scheduler、kube-proxy、coredns×2、calico 全家,全部 Running。【实测】
- L4:组件异常排查 `kubectl get pod -n kube-system` + `describe` + `logs`。
- L5:单节点全挤一台 vs 生产 3 master + etcd 独立多副本 + 多 AZ。
- L6:"你说下 Pod 创建的完整流程?" → 提交到 API Server → 存 etcd → Controller 创建 ReplicaSet → Scheduler 打节点 → kubelet 调 containerd 起容器 → 上报状态。这一串我踩 NFS 制备器坑时完整用过(describe 看 Events 就是看这条链上哪一环断了)。
- L7:高可用生产化(L6 质疑单节点的答案)。

### ③ containerd + nerdctl(防伪核心)

- L1:容器运行时(管镜像和容器生命周期);nerdctl 是它的命令行工具,用法接近 docker。【原理】
- L2:K8s 1.24 移除 dockershim,直接对接 containerd;Docker 内部本来就调用 containerd,直接用它少一层、更轻。**K8s 节点不需要 Docker**。【原理+实操验证】
- L3:**containerd 有命名空间隔离,K8s 的镜像都在 `k8s.io` 里,nerdctl 默认看 `default`**,必须在 `/etc/nerdctl/nerdctl.toml` 配 `namespace = "k8s.io"` 才看得到集群镜像;`cgroup_manager = "systemd"`;sock 地址 `/var/run/containerd/containerd.sock`。【实操】
- L4:加速配置在 `/etc/containerd/certs.d/<域名>/hosts.toml`,可配多个 mirror 依次尝试、失败自动切换(比 Docker 的 registry-mirrors 灵活);我剔过失效源:中科大的已下线(域名解析不到)、南大返回 403、百度云解析失败,最终留 daocloud / 1ms.run / xuanyuan.me。【实操】
- L5:vs Docker(重、带 swarm 等多余功能)/ vs crictl(K8s 专用调试,不含 build/push)。
- L6:"你连 Docker 命令都不用,怎么排查容器?" → nerdctl ps/logs/exec 用法一样,`nerdctl -n k8s.io images` 看集群镜像;这就是我踩 containerd 命名空间坑学会的。
- L7:生产一般也是 containerd;containerd 配置 `config_path = "/etc/containerd/certs.d"` 让它读加速目录。【实测确认过】

### ④ buildkit(L3 专属细节,防伪利器)

- L1:镜像构建引擎,nerdctl build 的后端。
- L2:不用它 `nerdctl build` 直接报 `buildctl not found`(我真踩过);它是下一代构建架构,和 dockerd 解耦。
- L3:下载 v0.16.0 二进制,写 systemd service,关键参数 `--containerd-worker-namespace=k8s.io`;**它有独立配置** `/etc/buildkit/buildkitd.toml`:docker.io 走 daocloud 加速、Harbor 走 http+insecure——不配就卡在 load metadata。【实操】
- L4:报错先看 `journalctl -u buildkit`。
- L5:vs 传统 docker build / vs kaniko(集群内无 root 构建,CI 接全自动时的规划选项)。
- L6:"三套镜像加速为什么要配三套?" → containerd、buildkit、Docker 是三个独立程序,各读各的配置,只配一处其他不生效。三套我都亲手配过。【实操】
- L7:【规划】接 Jenkins 全自动时用 kaniko 在集群内构建(不需要 Docker 守护进程,更安全)。

### ⑤ Calico(L1/L2/L4)

- L1:CNI 网络插件,负责给 Pod 分配 IP、打通 Pod 间和跨节点通信。【原理】
- L2:K8s 只定义网络标准接口 CNI,不实现网络;没它 Pod 起来没有可用网络。
- L3:Sealos 一次性装的 v3.28.1;装完 Pod 拿到 Calico 网段 IP(测试 Pod 拿到 100.82.50.71)。【实操】
- L4:**CRD 时序坑**:第一次报 `no matches for kind "Installation" in version "operator.tigera.io/v1"`——Calico 用 Operator 部署,CRD 还没注册完就去建资源了;原样重跑一次就成功。【实测】
- L5:vs Flannel(简单,只有网络)/ Calico(网络策略NetworkPolicy支持好)。生产常见这两个。
- L6:"Calico 挂了会怎样?" → 已运行 Pod 不受影响但新建 Pod 拿不到 IP 卡在 ContainerCreating;我是从 CRD 报错这个角度理解的,没实际拔过。
- L7:【原理】网络策略 NetworkPolicy 未实操。

### ⑥ NFS + StorageClass(存储三件套,高频)

- L1:PV 是实际存储卷的登记,PVC 是应用的申请单,StorageClass 是自动建 PV 的中介;NFS 是底层网络共享存储。【原理+实操】
- L2:容器重启数据丢,持久化数据必须外挂;动态供给让用户只提交 PVC、管理员不用手动建 PV。
- L3 完整链路:NFS 服务端(`dnf install nfs-utils` → `/etc/exports` 写 `/data/nfs *(rw,sync,no_root_squash,no_subtree_check)` → `exportfs -rv` → `showmount -e` 验证)→ 部署 `nfs-subdir-external-provisioner` v4.0.2(全套 yaml:SA/ClusterRole/Deployment/StorageClass)→ StorageClass 名 **nfs-storage**,注解 `storageclass.kubernetes.io/is-default-class: "true"` 设为默认 → 【实测】提交 1Gi 测试 PVC → 状态 Bound,`/data/nfs` 下自动生成子目录。
- L4:**ImagePullBackOff 坑**:制备器镜像 `registry.cn-hangzhou.aliyuncs.com/google_containers/nfs-subdir-external-provisioner` 根本不存在,describe 的 Events 报 `repository does not exist`(不是网络问题!)→ 先 `nerdctl pull` 验证新地址能拉,再 `kubectl set image` 热替换。【实操,主推排障故事之一】
- L5:vs local-storage / 云盘 PV(NFS 搭建最快,学习首选;生产重要数据一般用分布式存储或云盘)。
- L6:"为什么设默认 StorageClass?" → PVC 不写 storageClassName 就自动用它,应用清单更简洁;这是我实测 1Gi PVC 自动 Bound 的前提。
- L7:【原理】accessModes(RWO/ROX/RWX)、回收策略 Retain/Delete 知道概念,未实操切换。

### ⑦ Ingress-nginx(流量入口)

- L1:Ingress 是七层路由规则(按域名/路径转发),Ingress-nginx 是执行规则的控制器;IngressClass 指明规则由哪个控制器实现。【原理】
- L2:集群需要一个统一入口做七层转发和路由,不能每个服务都开 NodePort。
- L3:Helm 仓库 kubernetes.github.io 国内不通,改用 ghfast.top 代理下载 baremetal 版 deploy.yaml,`sed` 把镜像换成国内可拉的 dyrnq 版(替换时要去掉 @sha256 digest);apply 后 patch 成 **hostNetwork: true + dnsPolicy: ClusterFirstWithHostNet**,让 Ingress 直接占宿主机 9443/8543;controller Pod IP 就等于节点 IP,curl 返回 404 说明已接管但无路由。【实操】
- L4:**端口连环坑**(主推):改 8080 → CrashLoopBackOff,`kubectl logs --previous` 显示 `port 8080 is already in use`(被 ingress-nginx 容器内部占用);8443 被 validating-webhook 占用 → 最终 HTTP 9443 / HTTPS 8543。教训:改中间件端口前先搞清它内部已占哪些端口;CrashLoopBackOff 必须看 --previous(当前容器日志是空的)。【实测】
- L5:单节点用 hostNetwork / 生产用 LoadBalancer 或 NodePort+外部 LB(因为 hostNetwork 有端口冲突风险、隔离性差)。
- L6:"为什么不用 NodePort?" → hostNetwork 直接占 80/443 等价端口更接近生产形态,且当时是跟着 baremetal 方案走的;NodePort 也可行,只是多一层端口映射。
- L7:【未做】HTTPS 证书没配(cert-manager/自签是规划)。

### ⑧ Harbor(镜像仓库)

## 1.7 踩坑故事库(18 个真实坑,每个都是弹药)

讲坑公式(模拟面试打磨过的):**现象 → 怎么定位(带命令) → 根因 → 怎么解决 → 学到什么**。

### 主推 Top 3(被问"讲个排障经历"首选)

**#1 containerd 冲突(防伪第一细节)【实测】**
现象:`sealos run` 报 `containerd is installed ... please uninstall it first`。
定位:看报错明确是冲突;复盘发现装 Docker 时把 containerd.io 一起装了,而 Sealos 要自己装并管理 containerd,拒绝复用。
解决:`systemctl stop docker containerd` → `dnf remove -y docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin` → `rm -rf /var/lib/docker /var/lib/containerd /etc/containerd`(不清理残留重跑还报错)→ 重跑成功。
升华:K8s 节点其实不需要 Docker(1.24 移除 dockershim);卸载软件不能只 remove 包,残留目录要清。

**#2 NFS 制备器 ImagePullBackOff(体现会看 Events)【实测】**
现象:制备器 Pod 一直 ImagePullBackOff。
定位:`kubectl describe pod` 看 Events,报 `pull access denied, repository does not exist`——关键在文案:不是超时/连接失败,是"仓库不存在",所以不是网络问题是地址错。
解决:换 `dyrnq/nfs-subdir-external-provisioner:v4.0.2`,先 `nerdctl pull` 手动验证能拉,再 `kubectl set image` 热替换。
升华:排查镜像问题先分清"网络不通"还是"镜像不存在",看 Events 的具体报错文案,别一看拉不下来就瞎换源。

**#3 备案拦截三连(体现懂机制)【实测】**
现象:Harbor 第一次能打开,刷新就跳阿里云"备案状态不符合访问要求"页。
定位:这是阿里云**旁路异步扫描**——首次请求穿透成功,检测系统发现未备案域名后加入网关拦截名单,之后请求在网关层就被劫持,根本没到服务器。用"内网 curl 通不通"验证服务本身正常,确认是网关拦截。
尝试与排除:改 9443 非标端口→**无效**,拦截依据是 HTTP 的 **Host 头域名**,不看端口;换成解析到 127.0.0.1 的 nip.io 域名 + SSH 端口转发,HTTP 封在 SSH 加密隧道里网关读不到 Host 头→通。
升华:排查要先搞清"拦截规则依据什么维度"(域名/端口/IP),思路才对;国内云用域名提供 Web 服务必须备案,绕过只是学习环境手段。

## 2.4 原理深挖(七层)

### WAF 本体

- L1:Web Application Firewall,应用层防火墙,我的是**反向代理模式**——客户端不直接访问后端,所有流量先到 WAF,检测引擎分析后决定放行转发或拦截。【实操】
- L2 为什么独立部署(四条,背熟):①减少影响范围(WAF 影响所有流量);②避免端口冲突(WAF 要占 80/443);③资源隔离(检测耗 CPU/内存);④故障隔离(WAF 挂了不连累后端排查)。【原理+实操验证:80 冲突真实发生过】
- L3 配置:防护应用四字段——域名 / 端口(80) / 接入方式(代理到已有应用) / 上游服务器(http://192.168.121.101);上游服务器=后端真实 Web 服务器。
- L4:见 2.5 坑。
- L5 对比:WAF(七层看 HTTP 内容)vs 传统防火墙(三/四层看 IP 端口);WAF(带安检的反代)vs Nginx(纯转发);雷池底层是 Tengine 系。
- L6:"WAF 拦截原理/检测什么?" → 攻击防护(SQL 注入/XSS/代码注入/RCE/路径遍历/XXE)、CC 防护(频率限制)、Bot 防护(人机验证)、身份认证(等待室/密码保护)。我实测了 SQL 注入类 payload。【实测】
- L7:【未做/边界】SLB 未实操(单台 ECS 不需要,按小时收费);社区版**没有自动配置同步**,双节点配置是我手动保持一致的(企业版才有);误拦加白名单——原理清楚,我没遇到过真实误拦。

### SSL 卸载【实操】

- HTTPS 流量到 WAF 的 443 解密(卸载),WAF 之后到后端走 HTTP 8080。三大好处:后端省加解密资源、证书统一在 WAF 管理、内网段可信。
- 追问"后端走 HTTP 安全吗?" → 流量在 WAF 与后端之间,配合"后端只监听 127.0.0.1 不暴露公网"收口;生产可用内网 HTTPS 或 mTLS 再加固。

### 证书体系【实操+原理】

- DV(域名验证,免费,几分钟,我用的阿里云免费 DV 90 天)/ OV(组织验证,收费 1-3 天)/ EV(扩展验证,浏览器显示企业名,金融电商用)。
- 注意点(我实际遇到的):免费 DV 是**单域名证书不含子域名**(img.chenshihao.cn 得另配);90 天到期要续。

### OSS 防盗链【实测】

- 原理:浏览器请求图片带 **Referer** 头标识来源页面,OSS 检查是否在白名单(https://chenshihao.cn、https://*.chenshihao.cn),不在返回 AccessDenied denied by bucket referer policy;空 Referer 不允许→防直接复制 URL。
- 实测:白名单外直接访问被拒;从站点内引用正常显示。
- L5:"Referer 能伪造吗?" → 能,curl -e 就行;更强的是**签名 URL**(带时效签名);我讲的是够用层,生产配合 CDN 鉴权。

### CDN + OSS【实操】

- 原理:img 子域 CNAME 到 CDN,用户就近边缘节点取缓存,没有才回源 OSS;省 OSS 流量费(CDN 更便宜)、提速、防源站被打。
- 我的真实问题:**CDN 回源时 Referer 与 OSS 防盗链白名单不匹配 → 403**,这是 CDN+OSS 防盗链经典问题,生产要在 OSS 白名单加 CDN 回源 Referer 或改用鉴权 URL。我实测到"回源链路已通但被防盗链拦"这一层。【实测+原理】
- 顺序问题:"CDN 和 WAF 谁在前?" → 我的架构里静态图片走 img 子域 CDN 直连 OSS(不过 WAF),主站动态流量走 WAF——静态动态分流;如果同一个域名既走 CDN 又走 WAF,通常 CDN 在前做缓存,安全检测在回源层做。
