# 踩坑与排障记录

两次环境搭建（云端 ECS 集群 + 本地 VM）遇到的所有实质性问题，按类别整理。每条记录现象、定位过程和根因。排障过程比顺利执行学到的东西多。

## 一、环境准备

### 1. 按量付费 ECS 整点无法释放

**现象**：凌晨 3 点释放实例失败，提示"按量付费实例正在结算中"。
**根因**：按量付费每小时整点出账，出账窗口期内实例状态锁定。
**处理**：等几分钟过了结算窗口再释放。

### 2. 选错镜像/GPU 规格

重装系统时页面第一个选项是"Alibaba Cloud Linux with GPU Driver"，差一点选上——33G 的大家伙，而且按量付费的 GPU 实例是另一个价格量级。选型时看清规格族。

### 3. 一条命令卡半小时：`conntrack-tools` 拼写

**现象**：`yum install -y conntrack-tools` 卡住不动。
**根因**：多打了个 s，yum 在全网仓库里搜不存在的包名。
**教训**：命令卡住先检查输入，再怀疑网络。长包名复制粘贴，不手敲。

### 4. tmux 窗口"卡死"

**现象**：tmux 里终端完全无响应。
**根因**：误按了 `Ctrl+B S`（冻结窗格）。
**处理**：`Ctrl+B Q` 解冻。

## 二、网络与镜像源（大陆云环境的老大难）

### 5. Docker 官方源连不上

`download.docker.com` 直接超时，换阿里云镜像源。大陆环境的常规第一步。

### 6. USTC 镜像站部分服务下线

配了 `mirrors.ustc.edu.cn` 的 docker-ce 源，404。中科大镜像服务在收缩，换 `mirrors.cloud.tencent.com` 正常。**文档里写的源不一定还活着，以实际 curl 通不通为准。**

### 7. 镜像加速要配在三个地方

配了 registry-mirrors 还是拉不动，因为配错了组件：

| 组件 | 配置文件 |
|---|---|
| Docker | `/etc/docker/daemon.json` |
| containerd（K8s 拉镜像走这里） | `/etc/containerd/config.toml` 的 registry mirrors 段 |
| nerdctl（手动 build/push 走这里） | `/etc/nerdctl/nerdctl.toml` |

K8s 里 Pod 的 ImagePullBackOff 和手动 `docker pull` 通不通，是完全不同的两套配置。**排查镜像拉取问题，先想清楚"谁在拉"。**

### 8. sealos 拉 Kubernetes 组件镜像极慢

`sealos run` 下载镜像花了 6 分钟以上，一度以为卡死。labring 镜像源速度就这样，丢 tmux 里跑完即可。

## 三、K8s 安装

### 9. `failed to run Kubelet: run containerd: containerd is already running`

**现象**：sealos 装集群报这个错，kubelet 起不来。
**根因**：先装了 docker-ce，它带一个独立运行的 containerd 守护进程，和 sealos 要管理的 containerd 冲突。
**处理**：`yum remove docker-ce docker-ce-cli containerd.io`，只留 sealos 装的 containerd + nerdctl。K8s 1.24 之后本来就不需要 Docker。

### 10. `helm: command not found`

sealos 完成前的早期阶段 helm 还没装好。等 sealos 全部跑完再操作。

### 11. Calico 安装后 kubectl 卡住，接着 Connection refused

**现象**：apply calico.yaml 之后所有 kubectl 命令卡死，然后 API Server 拒绝连接。
**根因**：apply 瞬间 Calico 的 CRD 还在注册，API Server 短暂过载。
**处理**：等 30~60 秒自己恢复。不是故障，是 CRD 注册的时序问题，但第一次遇到很吓人。

### 12. SSH 断开导致安装中断

长时间安装挂在 SSH 会话里，网络一抖前功尽弃。**所有超过几分钟的操作都放 tmux/screen 里跑。**

## 四、存储

### 13. NFS provisioner 镜像 `InvalidImageName`

**现象**：`registry.k8s.io/nfs-subdir-external-provisioner:v4.0.18` 拉不到。
**根因**：这个版本号不存在。教程抄来的 tag，作者本地有缓存所以能跑，registry 里根本没这个版本。
**处理**：去掉 `:v4.0.18` 用默认 tag，正常拉起。
**教训**：教程里的版本号不要盲信，先 `nerdctl pull` 验证镜像存在再往 yaml 里写。

## 五、入口与备案

### 14. 未备案域名访问 80 端口被拦截

**现象**：域名解析到 ECS 后，访问返回备案提示页而不是应用。
**定位**：最开始怀疑 Ingress 配错——直到把本地 `/etc/hosts` 直接指过去访问正常，才确认是经过公共 DNS 解析的未备案域名在 80 端口被云平台拦截。请求根本没到我的机器。
**处理**：学习环境用隧道转发 + 非标端口绕行（见 16）。生产环境没有绕行这一说，必须备案。

### 15. 端口连环冲突

| 占用方 | 端口 | 处理 |
|---|---|---|
| Ingress-nginx（hostNetwork） | 30080/30443 | 环境入口，保留 |
| sshd | 22 | 保留 |
| frpc（隧道客户端） | 22→8888 | 改用 8888 |
| docker-proxy（早期映射残留） | 8090 | `docker ps` 找到后清掉 |

`bind: Address already in use` 这类报错都沿这条链清。**动手前先 `ss -tlnp | grep <端口>` 确认占用。**

### 16. 隧道转发 + hosts 的完整绕行方案

1. 云主机跑 frpc（frp 客户端），把服务端口通过隧道映射到本机的 8888
2. `/etc/hosts` 把 `gitea.local`、`harbor.local` 等域名解析到 `127.0.0.1:8888`
3. `nerdctl login harbor.local:30443` 走 hosts 解析，经隧道连到本地 Harbor

**排障**：frpc 映射后 `ss -tlnp | grep 8888` 显示监听，但 `curl harbor.local:30443` 还是 connection refused——nerdctl login 依赖 hosts 静态解析，这和"服务监听在 8888"是两回事，hosts 没配对，隧道通了也连不上。**分层验证：先验证隧道通（curl 127.0.0.1:8888），再验证域名解析（curl harbor.local:30443）。**

## 六、CI/CD（本地 VM 阶段）

云服务器释放后，在本地 VMware 虚拟机（4C8G，Rocky Linux 9）用 docker 重建了 Gitea + Jenkins。这一阶段的坑：

### 17. 流水线永远 "Waiting for next available executor"

**现象**：Jenkins 构建排队不动，executor 明明空着却不调度。
**定位**：节点管理里 Built-In Node 显示离线。
**根因**：**磁盘满了**。Jenkins 有磁盘空间监控，根分区剩余低于阈值（默认 1G）会自动把节点标记离线，防止构建写崩磁盘。`df -h` 显示 96% 已用——反复 build 的 docker 镜像把盘吃满了。
**处理**：`docker system prune -a -f` 清出 4.6G，节点恢复在线，构建立刻开始执行。
**教训**：构建卡住别只盯构建日志，先看节点状态；跑 CI 的机器要盯磁盘水位，docker 镜像增长速度远超直觉。

### 18. `couldn't find remote ref refs/heads/master`

**现象**：Pipeline from SCM 拉代码失败，报找不到 master 分支。
**根因**：仓库默认分支是 **main**（新版 Gitea/Git 的默认值），任务里 Branches to build 填的是教程里的 `*/master`。
**处理**：改成 `*/main`。
**教训**：教程的年代差异体现在细节里——分支名、版本号、配置项默认值，都要以自己环境的实际状态为准。

### 19. Jenkins 插件源超时（离线环境）

**现象**：插件管理页打不开，更新源检查超时。
**根因**：Jenkins 默认 update center 在海外。
**处理**：更新源换成清华镜像 `https://mirrors.tuna.tsinghua.edu.cn/jenkins/updates/update-center.json`。和 yum/pip/镜像源是同一类问题，凡是海外默认源都先换镜像。

## 七、排障方法论总结

这些坑排下来，沉淀出几条固定动作：

1. **分段定位**：链路任何一环不通，先把链路切成段，逐段验证。隧道问题的"先 curl IP:port 再 curl 域名"就是典型——一次只验证一跳。
2. **先怀疑输入，再怀疑环境**：命令卡住先看拼写，配置不生效先看改的是不是正确的文件（三套镜像加速配置）。
3. **改一步验一步**：每次只改一个变量，立刻验证效果。批量改完再测，出问题不知道是哪一步引入的。
4. **看事件和前日志**：`kubectl describe`（事件）→ `kubectl logs --previous`（崩溃前日志）→ `describe svc` → `get endpoints`，按这个顺序走，大部分 K8s 问题能定位到层。
5. **状态类问题先看监控面**：Jenkins 节点离线、ECS 结算锁定这类，是平台的保护机制在起作用，先去状态页/控制台看，比自己瞎试快。
