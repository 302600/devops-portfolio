# 架构与流水线说明

这份文档说明这套 K8s DevOps 环境的整体结构：用了哪些组件、为什么选它们、一次发布在系统里怎么流动。具体的安装命令在《01-搭建实录》，本地 VM 的 CI 搭建过程在《04-Jenkins本地CI流水线搭建实录》。

## 环境

| 项 | 值 |
|---|---|
| 服务器 | 阿里云 ECS，4C16G，Rocky Linux 10.2，按量付费（约 1.1 元/小时） |
| 集群 | 单节点 K8s 1.34（sealos 部署），master 去污点同时跑业务 |
| 状态 | **云服务器已释放**（按量付费，学完关机止损）；CI 环节已在本地 VMware 虚拟机（4C8G）重建并跑通，见 04 |

单节点是学习成本考虑：多节点要加钱，而"多节点 Pod 飘走、存储跟随"这套行为用 NFS 动态供给在单节点上也能验证。

## 总体架构

```
浏览器/客户端
   │  http://<公网IP>.nip.io:30080 / :81 / :3000 / :8888
   ▼
Ingress-nginx（hostNetwork 模式，占宿主机 30080/30443）
   │
   ├── myapp        → Service → Pod（demo-app，镜像来自 Harbor）
   ├── gitea        → Service → Pod（代码仓库）
   ├── harbor       → Service → Pod（镜像仓库）
   ├── jenkins      → Service → Pod（CI）
   └── argocd       → Service → Pod（CD）
          ▲                          │
          │ watch Git                │ kubectl apply / Image Updater
          │                          ▼
   gitea/demo-config (config-repo)  集群内资源
                                        │
   镜像: nerdctl build → harbor.local:30443/demo/demo-app:vN
   配置: myapp-config ConfigMap → NFS 动态 PVC（nfs-csi StorageClass）
```

## 组件选型记录

选型的统一原则：**单节点 16G 内存是硬约束，能省则省，但流程不能简化**——要的是完整的 CI/CD 形态，不是最省资源的玩具。

| 组件 | 选择 | 理由 |
|---|---|---|
| K8s 部署 | sealos | 一条命令装完集群+Calico+Helm，比 kubeadm 省掉证书和各组件的手动配置 |
| 容器运行时 | containerd + nerdctl | K8s 1.24+ 的默认运行时；nerdctl 提供类 Docker CLI，直接对 containerd 构建镜像 |
| CNI | Calico | 主流选择之一，sealos 默认集成 |
| 存储 | NFS + nfs-subdir-external-provisioner | 学习成本最低的云原生存储方案：PV/PVC/StorageClass/动态供给全套概念都能练到，而且 NFS 目录在 Pod 之外，Pod 重建数据还在 |
| 入口 | Ingress-nginx，hostNetwork 模式 | 单节点没有云厂商 LB 可用，hostNetwork 让 Ingress 直接占用宿主机端口；配 nip.io 通配域名，不用改 hosts 文件就能按域名路由 |
| 镜像仓库 | Harbor（Helm 安装） | 生产最常用的私有仓库；安装时关掉 trivy 扫描和 notary，压内存 |
| 代码仓库 | Gitea | 同类里最轻（几百 MB 内存），GitLab 在这个内存量级跑不动 |
| CI | Jenkins | 装机量最大的 CI 工具，Pipeline 语法是通用技能 |
| CD | ArgoCD | GitOps 代表工具：Git 是期望状态的唯一来源，控制器持续对账 |

资源账（云服务器版本）：

| 组件 | 大约占用 |
|---|---|
| 系统 + K8s 基础 | ~4.5 G |
| Harbor（已精简） | ~1.5 G |
| Gitea + Jenkins | ~2 G |
| ArgoCD + demo 业务 | ~1 G |
| 峰值合计 | ~9-10 G / 16 G |

## 一次发布的完整数据流

以发布 demo-app v2 为例，云环境下的完整链路：

1. **代码**：改 `index.html` v1 → v2，`git push` 到 Gitea 的 `demo-app` 仓库
2. **构建**：`nerdctl build -t harbor.local:30443/demo/demo-app:v2 .`
3. **推送**：`nerdctl push` 到 Harbor（配了 hosts 解析 + insecure registry 免证书）
4. **配置**：改 `demo-config` 仓库 `deployment.yaml` 里的镜像 tag v1 → v2，`git push`
5. **同步**：ArgoCD 轮询发现 Git 与集群漂移，自动 `kubectl apply`（或 Image Updater 检测到新 tag 自动改配置仓库）
6. **滚更**：Deployment 触发滚动更新，先起新 Pod，就绪探针过了才切流量、杀旧 Pod——全程服务不断
7. **数据**：`myapp-config` ConfigMap 改动 →  Deployment 重启 → 新 Pod 挂载同一份 NFS PVC，内容更新且持久化

第 2、3 步在云环境里是手动执行的（当时 Jenkins 只跑通了 pipeline 语法，没接构建）。这就是后来本地 VM 版本重点补齐的环节。

## CI 的两次实现

**第一次（云端集群）**：CI 半自动——构建推送靠手敲，CD（ArgoCD）全自动。跑通了 GitOps 那一半，但"提交代码就自动出镜像"这一半没闭环。

**第二次（本地 VM，服务器释放后重建）**：Gitea + Jenkins，流水线定义为仓库里的 Jenkinsfile：

```groovy
pipeline {
    agent any
    stages {
        stage('拉取代码') { steps { checkout scm } }
        stage('构建镜像') { steps { sh 'docker build -t demo-app:${BUILD_NUMBER} .' } }
        stage('部署') {
            steps {
                sh '''
                    docker rm -f demo-app || true
                    docker run -d --name demo-app -p 8090:80 demo-app:${BUILD_NUMBER}
                '''
            }
        }
    }
}
```

触发用 Jenkins 自带的 Poll SCM（`H/1 * * * *`，每分钟轮询），没装 webhook 插件——少一个依赖，演示环境够用了。push 代码后 1~2 分钟内自动构建、自动部署，页面内容更新，闭环验证通过。详细过程和踩坑见《04-Jenkins本地CI流水线搭建实录》。

本地 VM 版的部署目标是普通 docker 容器而不是 K8s Pod，这是环境限制（4C8G 跑不动 K8s + Harbor + ArgoCD 全家桶），但 Jenkins Pipeline 的核心——代码即流水线、SCM 触发、构建部署自动化——是同一件事。

## 已知边界

- 单节点：没有多副本调度、节点故障转移的实际演练
- 无监控告警体系（Prometheus/Grafana 未接）
- 全 HTTP 内网，没有 TLS 证书
- 备案绕行方案（隧道转发 + 非标端口）只适用于学习环境，生产不合规
- 云服务器已释放，集群部分目前是文档状态，可随时按 01 实录重建（按量付费，建一次约 1 元/小时）
