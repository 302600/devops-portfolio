# 第 1 章 容器到底是什么

## 1.1 从一个千古难题说起

软件开发圈流传一句话:"在我电脑上是好的。"

一个程序要跑起来,靠的不只是代码本身,还有它的**运行环境**:操作系统版本、语言运行库、依赖库的版本、配置文件、环境变量……任何一项对不上,程序就罢休。你自己的经历就是证据:装 Docker 时官方源连不上、换阿里云源;中科大镜像站下线了、换 daocloud——**装环境这件事,本身就是运维痛苦的大头**。

虚拟机给出了第一种答案:把整个操作系统连同环境一起打包。彻底,但昂贵——每台虚拟机都带一套完整内核,动辄几个 GB,启动要几十秒到几分钟,一台 16G 的机器撑死跑十几台。你在 WAF 项目里把 hadoop103 从 1G 调到 2G 内存时应该有体感:虚拟机是"重量级住户"。

容器的答案是:**不打包操作系统,只打包应用程序和它的依赖,然后让所有容器共享宿主机的内核**。

## 1.2 容器的本质:隔离,而不是虚拟化

这是全书最重要的一个认知,先说结论:

> **容器不是"轻量级虚拟机"。容器就是一个普通的 Linux 进程,只不过被内核做了两件事:让它"看不见"别人,让它"用不超"定额。**

Linux 内核提供了两套机制:

**① namespace(命名空间)——管"看见什么"**

namespace 把进程圈进一个独立的世界,让它以为自己是唯一的:

| namespace | 隔离的内容 | 白话 |
|---|---|---|
| pid | 进程号 | 容器里自己的 1 号进程,看不见宿主机的其他进程 |
| net | 网络栈 | 自己的网卡、IP、端口,所以容器可以各自都"监听 80" |
| mnt | 挂载点/文件系统 | 看到的根目录 `/` 是容器自己的,不是宿主机的 |
| uts | 主机名 | 容器可以有自己的 hostname |
| ipc | 进程通信 | 隔离信号量、共享内存等 |

**② cgroups(控制组)——管"用多少"**

namespace 解决"看见",cgroups 解决"配额":给这组进程划定 CPU 用几核、内存上限多少、磁盘 IO 多少、最多开多少进程。超了内存上限就是 OOM,进程被内核杀掉——你面试背过的"OOM Kill",执行者就是 cgroups 机制。

**比喻**:虚拟机是每户盖一栋楼(连地基/水电系统——内核——都各带一套);容器是同一栋楼里隔出来的精装公寓(共享地基水电,但每户有自己的门锁、电表和水表)。

由此推出容器的所有特性,你不用背,自己推:
- 启动快 → 因为只是"启动一个进程",不是引导一个操作系统;
- 体积小 → 因为不带内核(几十 MB 的 nginx:alpine 就是这么来的);
- 密度高 → 因为没有每台"楼"的地基开销;
- 隔离不如 VM 强 → 因为共享内核,内核出漏洞理论上影响所有容器(所以安全敏感场景有 kata containers 这类"容器+轻 VM"方案)【延伸】。

## 1.3 镜像:把环境做成只读模板

进程要跑,得先有文件系统。镜像就是"程序 + 依赖 + 环境"打包成的**只读模板**。

镜像的核心技术是**分层 + 联合挂载**:

- Dockerfile 里的指令,**凡是会改动文件系统的**(RUN、COPY、ADD)各生成一层;**只声明元数据的**(CMD、EXPOSE、ENV)不生成层,只是附加信息。
- 多层像千层饼一样叠起来,通过联合挂载(overlayfs)合成一个完整的文件系统视图。
- **层可以被复用**:两个镜像如果 `FROM` 了同一个基础镜像,那一层在磁盘上只存一份,pull 时也只拉本地缺的层。这就是为什么 `FROM nginx:alpine` 的构建和拉取都很快。
- **写时复制(Copy-on-Write)**:容器启动时,在镜像层顶上挂一个**可写层**,所有修改写进可写层,镜像层永远只读。读文件从上往下找,写文件先把底层文件拷到可写层再改。

**关键推论(第 6 章存储的伏笔)**:删除容器 = 丢掉可写层。所以**容器里产生的数据默认随容器蒸发**——这不是缺陷,是设计;需要持久的数据必须挂到容器外(数据卷/外部存储),这正是你项目里 NFS 那套存在的原因。

**回到你的操作**——你 demo-app 的 Dockerfile 一共四行,逐行拆:

```dockerfile
FROM nginx:alpine                                    # 第1层:官方 nginx 的 alpine 版(alpine=极小的Linux发行版,~5MB,所以整个镜像只有24.86MB)
COPY index.html /usr/share/nginx/html/index.html     # 第2层:把你的网页拷进 nginx 默认站点目录(nginx 配置里 root 指向这里)
EXPOSE 80                                            # 元数据:声明"我用80端口"(给人和工具看的说明,不产生层,也不真正开端口)
CMD ["nginx", "-g", "daemon off;"]                   # 元数据:容器启动时执行的命令
```

为什么 `daemon off;`?nginx 默认以守护进程方式运行(自己退到后台),但**容器里 PID 1 必须前台运行**——PID 1 退出,容器就退出。让 nginx 前台跑,它活着,容器就活着。这就是"容器的主进程要前台运行"的原因,也是很多程序进容器要改启动方式的原因。

## 1.4 再深一层(面试纵深)

- **docker stop 发生了什么**:先向 PID 1 发 SIGTERM(礼貌请求退出),默认等 10 秒,还活着就 SIGKILL(强杀)。所以应用要正确处理 SIGTERM,否则每次停容器都挨 10 秒+强杀【延伸】。
- **tag 是指针,digest 才是唯一身份证**:同一个 tag(如 latest)可以被重新指向新镜像;`@sha256:xxx` 的摘要才不可变。你在替换 ingress-nginx 镜像时要去掉 `@sha256` digest,本质就是:国内镜像站的镜像和 digest 对不上,只能按 tag 引用。
- **为什么 alpine 场景要小心**:alpine 用 musl libc 而不是 glibc,极少数编译型程序会不兼容——知道这个坑存在即可【延伸】。

# 第 2 章 Docker、containerd、K8s 的三角关系

## 2.1 一段历史:K8s 为什么"抛弃"了 Docker

这段历史的逻辑线,比结论更重要:

1. **2013 年,Docker 爆红**,把"容器"从极客玩具变成大众工具。它不只是运行时,还带了构建(docker build)、分发(registry)、网络、Compose 等一整套。
2. **K8s 起家时**,市场上已有多种容器运行时,Docker 只是其一。K8s 为了兼容 Docker,专门写了一层胶水代码,叫 **dockershim**。
3. **标准化时代到来**:行业制定了两个标准——**OCI**(镜像格式和运行时的开放标准)和 **CRI**(K8s 定义的容器运行时接口)。标准化的意义:**组件可以拔插**。任何实现了 CRI 的运行时,K8s 都能直接用。
4. **问题来了**:dockershim 是 K8s 侧的专用胶水,Docker 又更新频繁,维护成本高。而 Docker 的底层本来就是调用 containerd——**既然大家都要走 containerd,为什么不直接对接它?**
5. **于是 K8s 1.24(2022 年)移除了 dockershim**,容器运行时直接对接 containerd。

**面试金句**:不是"K8s 不支持 Docker 了",而是"K8s 不再需要为 Docker 走专用通道了"——因为 Docker 的核心(containerd)已被直接采用,Docker 这层外壳对 K8s 来说是多余的。

## 2.2 containerd 长什么样

- **定位**:工业级容器运行时,负责**镜像管理(拉取/存储)和容器生命周期(创建/启动/停止)**。它就是 Docker 心脏被单独抽出来的那部分。
- **砍掉了什么**:Docker 里的构建(另有 buildkit)、Swarm 集群、默认的 bridge 网络管理这些面向开发者的功能——K8s 自己有网络方案(CNI),不需要它管。
- **内部分工**(概念级):containerd 收到创建请求后,为每个容器拉起一个轻量的 **shim** 进程做现场管家,真正"把进程关进 namespace 和 cgroups"的是 **runc**——runc 干完就退出,不留驻。所以你在宿主机上 `ps` 看到的容器相关进程是 containerd 和各容器的 shim,而不是 runc。
- **containerd 的 namespace(注意!这不是 Linux 的 namespace)**:containerd 自己还有一层"租户"概念,用来隔离不同使用者的镜像和容器。**K8s 的一切都放在 `k8s.io` 这个命名空间里;Docker 的放在 `moby`;手动操作默认在 `default`。**

## 2.3 回到你的操作:卸载 Docker 那一步,到底卸了什么

你当时为了让 Sealos 装 K8s,执行了:

```bash
systemctl stop docker containerd
dnf remove -y docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin
rm -rf /var/lib/docker /var/lib/containerd /etc/containerd
```

拆开看,这三行分别在干三件事:
1. **停服务**:正在运行的容器全部停止;
2. **卸包**:把 Docker 全家(客户端、守护进程、它自带的 containerd、构建插件、Compose 插件)从系统里移除;
3. **清数据**:这才是关键——`/var/lib/docker` 存着 Docker 的所有镜像层,`/var/lib/containerd` 存着 containerd 的数据,`/etc/containerd` 是配置。**不删这些,Sealos 装的新 containerd 启动时会读到旧数据,冲突依旧**。你踩的"卸了还报错"就是这个原因,清了残留才通。

**教训的原理版**:Linux 上卸载软件,卸的是"程序本体";数据目录和配置目录是另一回事。重装/换实现前先想清楚:我要不要保留数据?不要就清干净,否则残留状态会污染新环境。

## 2.4 工具对照:今后用什么命令操作容器

| 想干什么 | Docker 时代 | containerd 时代(你的环境) | 说明 |
|---|---|---|---|
| 看容器 | docker ps | **nerdctl ps** | nerdctl 用法刻意做得和 docker 一致,迁移零成本 |
| 看镜像 | docker images | nerdctl images | 记得 namespace 是 k8s.io |
| 进容器 | docker exec | nerdctl exec / kubectl exec | K8s 里优先 kubectl(走 API Server,能跨节点) |
| 看日志 | docker logs | nerdctl logs / kubectl logs | 同上 |
| 构建/推送 | docker build/push | **nerdctl build/push(需 buildkit)** | buildkit 详见第 8 章 |
| K8s 视角排障 | — | **crictl** | 面向 K8s 的调试工具,只有 Pod/容器概念,**没有** build/push——它是"排障用",不是"开发用" |

**面试一句话**:"节点上排查用 crictl 或 nerdctl;nerdctl 面向人、命令习惯接 docker;crictl 面向 K8s、按 Pod 组织;构建推镜像用 nerdctl + buildkit。"

# 第 3 章 K8s 是什么:数据中心的操作系统

## 3.1 问题:从"管 10 个容器"到"管 300 个容器"

假设你有一台机器、10 个容器,手动管理没问题:`docker run` 起来,挂了重启,完事。现在把规模换成**30 台机器、300 个容器**,手管立刻崩盘,因为新问题全冒出来了:

- 容器该放哪台机器?(资源够吗?负载匀吗?)
- 机器挂了,上面的容器怎么办?
- 某个容器崩了,谁来发现、谁来拉起?
- 发新版本,300 个容器怎么换?怎么保证用户无感?
- 容器 IP 天天变,服务之间怎么互相找到对方?
- CPU 不够时自动加、闲时自动减?

**K8s 就是这一整类问题的标准化答案。**它管理的是"一群机器上的一大堆容器",提供调度、自愈、扩缩容、服务发现、滚动发布、配置与存储管理。类比:**单机时代你用 Linux 管进程,K8s 时代你用 K8s 管"容器级"的进程——它是数据中心的操作系统。**

## 3.2 核心思想:声明式 + 控制循环(全书的钥匙)

K8s 与其说是一套软件,不如说是一种**工作方式**。先分清两种思维:

- **命令式**:你一步步告诉系统怎么做——"启动 3 个容器"(kubectl run)、"再启动 1 个"、"把那个删了"。人不盯着,状态就漂。
- **声明式**:你只提交一张**需求单**——"我要 3 个副本、用这个镜像"。至于怎么凑够 3 个、挂了怎么补,系统自己搞定。

K8s 全程声明式。支撑它的是一个朴素到极致的机制——**控制循环(Reconcile Loop)**:

```
观察实际状态 → 和期望状态对比 → 有差异就执行动作消除差异 → 回到观察,永不停止
```

就像**空调恒温器**:你设定 26 度(期望),它不停测温(实际),高了吹冷风、低了停机——它从不"一次性"完成任务,它永远在对账。

**这句话是理解 K8s 的万能钥匙**:K8s 里的一切组件——Deployment 控制器、Node 管理、甚至 ArgoCD(第 9 章)——全是这个循环的变体。以后任何 K8s 问题,先问自己:"这里谁是期望,谁是实际,谁在做循环?"

## 3.3 控制面组件逐个拆(它们各自是循环里的什么角色)

**kube-apiserver:唯一的大门**
集群里**所有**的读写都要过 API Server——kubectl 过、ArgoCD 过、kubelet 也过。为什么必须收口到一个门?
- 统一**认证**(你是谁)和**鉴权**(你能不能干这个);
- 统一**准入控制**(请求合规检查);
- 统一读写存储,保证并发安全(带乐观锁的资源版本 resourceVersion);
- 留下**审计日志**(谁在什么时候改了什么)。
**记法**:API Server 是"前台总机"——一切对外联系都走它,没有直连后台的通道。

**etcd:集群的记事本**
分布式键值数据库,存着集群的**全部状态**(你提交的每个 yaml、每个节点的信息、每个 Pod 的记录)。要点:只有 API Server 读写它;内部用 Raft 协议保证多副本一致性(概念级即可)。所以面试常问"状态存在哪"——**etcd;但读写必须经 API Server,不能绕过**。

**kube-controller-manager:几十个控制器的打包**
注意复数:它不是一个控制器,而是**几十个控制器的合集**,每个控制器盯一类对象。和我们最相关的:
- **Deployment 控制器**:盯着 Deployment,保证有对应的 ReplicaSet;
- **ReplicaSet 控制器**:盯着 ReplicaSet 的副本数,少了就建 Pod,多了就删;
- 还有 Node 控制器(节点失联打标记)、Job 控制器等。
它们全在跑第 3.2 节那个循环。**"Deployment 在监控状态"是错误说法——监控对比的是 Controller,Deployment 只是你写的那张需求单。**(你在模拟面试里栽过这个坑。)

**kube-scheduler:分房的人**
新 Pod 出现但没有归属节点时,Scheduler 出场:**先过滤**(这台机器 CPU 够吗?端口冲突吗?有污点吗?)→ **再打分**(哪台更空、镜像是不是本机已有)→ 给 Pod 绑定节点。注意:**Scheduler 只决定"放哪",不负责"跑起来"**——跑起来是 kubelet 的事。

**kubelet:每台机器上的现场经理**
运行在每个节点上,盯着"分到我这个节点的 Pod",替它们干活:调用 CRI(也就是 containerd)拉镜像、起容器;调用 CNI 配网络;挂载存储卷;持续把实际状态上报回 API Server。**它是控制循环里"执行动作"的那只手。**

**一张图记住分工**:

```
你提交 yaml ──► API Server ──► etcd(存期望)
                    ▲                │ 事件通知
                    │ watch          ▼
      kubelet 上报实际 ◄── Controller(对比期望vs实际,创建Pod对象)
                    │                │
              Scheduler(给Pod分节点)│
                    ▼                ▼
              kubelet 调 containerd 跑起来
```

## 3.4 一个 Pod 从提交到运行的全旅程(白话时序)

把上面的组件串成一条时间线,这就是你排障时的"链条":

1. 你 `kubectl apply -f deployment.yaml` → 请求到 **API Server** → 校验、鉴权通过 → 期望状态写入 **etcd**;
2. **Deployment 控制器**(watch 到新 Deployment)→ 创建一个 **ReplicaSet**;
3. **ReplicaSet 控制器**发现"要 1 个,现在 0 个" → 创建 Pod 对象——此时 Pod 还没分节点,状态 **Pending**;
4. **Scheduler** 看到未调度的 Pod → 过滤+打分 → 绑定到你的单节点(单节点没得选,但流程一样);
5. 节点上的 **kubelet** watch 到"有个 Pod 分给我了" → 调 **CNI**(Calico)给 Pod 分配 IP → 调 **containerd** 拉镜像、创建容器 → 上报状态;
6. 镜像拉完、容器起来、探针通过 → Pod 变 **Running/Ready**。

**排障的原理就藏在这条链里**:`kubectl describe pod` 看到的 **Events**,就是这条链上每一步的流水记录。Pod 卡住,就是在链条某一步断了——卡在 3(资源不足/污点)是 Pending,卡在 5 拉镜像是 ImagePullBackOff,起来了又死是 CrashLoopBackOff。**排障 = 在链条上找断点。**

## 3.5 回到你的项目

你 `kubectl get pod -A` 时看到的那一屏,现在每个名字都有着落了:etcd、kube-apiserver、kube-controller-manager、kube-scheduler 是控制面(当年全挤在你那一台机器上);kube-proxy 是每节点的 Service 转发执行者(第 4 章讲);coredns 是集群内的 DNS 服务器(ArgoCD 靠它解析 `gitea.devops.svc.cluster.local` 这种 Service 名字);calico-node/typha 是网络插件(第 5 章);csi-node-driver 是存储(第 6 章)。

另外两件你亲历的事,现在可以给出原理版解释:
- **时间同步为什么致命**:K8s 组件间全是 TLS 证书通信,证书校验对时间敏感,偏差大握手直接失败——集群起不来。chrony 不是可选项,是前提。
- **master 污点**:控制面组件默认被一层"污点"保护着(第 4 章细讲),Sealos 帮你把污点去掉了(`Taints: <none>`),你的单节点才能既当控制面又跑业务。

# 第 4 章 三大对象:Pod、Deployment、Service

## 4.1 Pod:为什么最小单位不是"容器"

初学者的直觉:容器都隔离好了,直接调度容器不就完了?K8s 却发明了 Pod 这一层,让**一个或几个容器**绑成一个调度原子。为什么?

- 有些进程天生要**蜜里调油**:主程序 + 日志收集器、主程序 + 配置刷新器。它们需要共享网络(localhost 直接互访)、共享存储卷、同生共死。这种组合,打包成一个 Pod,调度、伸缩、销毁都是一个动作。
- Pod 内的容器**共享同一套 network namespace**:同一个 IP、同一个端口空间,localhost 互通——这就是 Pod 内容器"像同一台机器上的进程"的原因。

你项目里 demo-app 一个 Pod 一个容器,最简单;但面试若问"什么场景一个 Pod 多个容器",答 sidecar(边车)模式,举日志收集或代理的例子。

## 4.2 Deployment 与 ReplicaSet:副本与自愈的实现

你的 deployment.yaml 里有三个关键段位,各自被不同的角色"消费":

```yaml
spec:
  replicas: 1          # ← ReplicaSet 控制器读:要维持几个副本
  selector:            # ← ReplicaSet 控制器读:哪些 Pod 归我管(按标签认领)
    matchLabels: { app: demo }
  template:            # ← ReplicaSet 控制器用:造新 Pod 的模板(Pod 该长什么样)
    metadata: { labels: { app: demo } }   # template 的标签必须能被 selector 匹配到,否则永远凑不齐
```

**自愈的原理**(把 3.2 的循环落到具体):

> ReplicaSet 控制器不停对比"期望副本数"和"实际存活数"。你手动 `kubectl delete pod`,它立刻发现少了一个 → 按 template 重建 → 几秒后新 Pod 起来。**所以"删 Pod 会重生"——Pod 是耗材,ReplicaSet 才是那个"要几个"的意志。想真删,删 ReplicaSet(或把副本数调成 0)。**

**滚动更新的原理**:改镜像 tag 提交后,Deployment 控制器创建一个**新 ReplicaSet**(新版本),新旧两个 RS 此消彼长:新 RS 逐步加 Pod、旧 RS 逐步减 Pod,全程服务不断。旧 RS 不删除而是缩到 0 保留——这就是 `kubectl rollout undo` 能一键回滚的原理(把旧 RS 重新扩起来)。你在 ArgoCD 界面看到的 v1→v2 切换,底层就是这套 RS 编舞。

## 4.3 Service:给易变的 Pod 一个不变的门牌

**为什么需要 Service**:Pod 的 IP 有两个致命问题——**重建就变**(自愈机制决定 IP 不稳定)、**容器网络外部进不来**。业务之间、用户与业务之间,总不能追着 IP 跑。Service 就是"一个稳定访问入口 + 自动负载均衡到一组 Pod"。

**ClusterIP 的实现真相(高频追问点,务必吃透)**:

> Service 的 ClusterIP 是一个**虚拟 IP**——它不属于任何网卡、没有任何进程监听它。它的本质是 **kube-proxy 在每个节点上写的 iptables(或 IPVS)规则**:当数据包的目标地址是 ClusterIP 时,规则把包**改写目标地址(DNAT)为某个真实 Pod 的 IP** 再发出去。

由此推论(全是面试考点):
- **ping ClusterIP 不通是正常的**:ping 走 ICMP,而 DNAT 规则只处理 TCP/UDP 流量——ICMP 没有规则接,自然没回应。但 `curl` 通。**"ping 不通 Service 但服务是好的"是经典现象,别当故障。**
- 负载均衡不在某个"中间服务器"上做,而是**分布式地**由每个节点的内核规则完成;
- kube-proxy 三种模式一句话:userspace(远古,淘汰)/ iptables(默认,规则线性匹配)/ IPVS(内核哈希表,大规模集群性能好,还支持更多调度算法)【延伸:你未实操切换,按原理讲】。

**Service 怎么找到 Pod**:靠 **selector 匹配 label**,不是靠名字:

```
Pod   labels: app=demo        ← 打标签,像给工人戴工牌
Service selector: app=demo    ← 按工牌找人,不认名字不认脸
```

匹配结果实时维护在 **Endpoints** 对象里(Pod 上线自动加、下线自动摘)。为什么不用名字关联?因为 Pod 名字带随机后缀、IP 会变,**只有标签是稳定的**。这套"松耦合"是 K8s 全篇的设计哲学。

**Service 四种类型一句话**:
- **ClusterIP**(默认):集群内部访问;
- **NodePort**:在每个节点开一个端口(30000-32767)暴露,外部访问 节点IP:端口;
- **LoadBalancer**:云平台上自动创建一个外部负载均衡器指向服务——需要云支持;
- **ExternalName**:把外部服务起个集群内别名,几乎不用。

你的单节点环境没有云 LB 给你用,所以外部入口选择了 Ingress(第 5 章)——这个"为什么不用 NodePort/LB"的决策链,面试讲出来很加分。

## 4.4 回到你的项目:demo yaml 逐字段归位

```yaml
apiVersion: apps/v1
kind: Deployment
metadata: { name: demo, namespace: demo }        # 名字与楼层(namespace 隔离)
spec:
  replicas: 1                                     # → ReplicaSet 控制器
  selector: { matchLabels: { app: demo } }        # → 认领 Pod 的规则
  template:
    spec:
      containers:
        - name: demo
          image: harbor.127.0.0.1.nip.io:9443/devops/demo:v2   # → kubelet 拉镜像的完整地址(第8章讲这地址怎么构成)
          ports: [ { containerPort: 80 } ]
---
kind: Service
spec:

```

另外,你集群里的 namespace 规划(devops / harbor / argocd / demo / ingress-nginx)对应 3.3 讲的隔离楼层:namespace 只做**逻辑隔离**(名字前缀、配额边界、权限边界),不是网络硬隔离——跨 namespace 的 Service 一样能用全名互相访问(ArgoCD 访问 devops 楼层的 Gitea 就是活例)。

# 第 5 章 让外网访问进来:Ingress 与集群网络

## 5.1 问题:Pod 藏在容器网络里,外网怎么进来?

Calico 给每个 Pod 分配的 IP(比如你的测试 Pod 拿到 100.82.50.71)是**容器网络的地址**——只在大网内部互通,公网根本路由不到。外网用户要访问服务,必须有人把流量"引进来"。K8s 提供三条路,各有代价:

| 方案 | 做法 | 代价 |
|---|---|---|
| NodePort | 每个节点开 30000-32767 的端口 | 端口丑(不能走 80/443)、每个服务占一个、没有七层能力 |
| LoadBalancer | 云厂商发一个外部负载均衡器 | **要云支持、按个收费**——你那台裸单节点没有 |
| **Ingress** | 集群统一开一个七层入口,按**域名/路径**把流量分发到不同 Service | 需要部署 Ingress Controller |

前两个的问题很清楚:服务一多,NodePort 管理爆炸,LB 一个服务一个太贵。Ingress 的思路是**收口**:整个集群一个大门,门卫按 Host 头和路径指路。你在项目里给 Harbor、Gitea、Jenkins、ArgoCD、demo 五个服务各配了一个 Ingress 规则,共享同一个 9443 入口——这就是"收口"的直观体现。

## 5.2 Ingress 是规则,Ingress Controller 是执行者

这是最容易混的一对概念:

- **Ingress 对象**:一份声明——"Host 是 demo.127.0.0.1.nip.io 的请求,转给 demo Service 的 80 端口"。它只是一段配置,**自己不处理任何流量**。
- **Ingress Controller(你用的是 ingress-nginx)**:真正站在门口的网关。它的工作方式很妙:**watch 集群里所有 Ingress 对象 → 把规则翻译成一份 nginx.conf → reload 生效**。

所以 ingress-nginx 的本质是:**一个会自动写配置的 nginx**。你 WAF 项目里手动改 nginx.conf 做反向代理的那些活,在这里变成了"提交一个 Ingress 对象,controller 自动生成配置"——这就是声明式的好处:你不再碰配置文件,只声明意图。

**IngressClass** 是"这份规则由哪个 controller 来实现"的指定(集群里可能同时有 nginx、traefik 等多种 controller)。

## 5.3 你的 hostNetwork 决策:为什么、代价是什么

裸金属/单节点环境没有云厂商给你发 LoadBalancer,Ingress Controller 的流量就出不去。解决方案就是 **hostNetwork: true**——让 controller 的 Pod **直接使用宿主机的网络栈和端口**,相当于把网关焊在服务器上,外网流量直进。

代价(面试必问):
- **端口独占**:Pod 占了宿主机 9443/8543,别的进程不能再抢——这正是你后来改端口的根源;
- **隔离性下降**:Pod 与宿主机共享网络命名空间,网络安全边界变弱;
- **调度绑定**:controller 实际上和这台机器绑死了(单节点无所谓,多节点要考虑)。

生产环境更常见的是 NodePort + 外部 LB,或云上的 LoadBalancer Service——你现在能讲清"学习环境用 hostNetwork、生产用 LB"的取舍,比背概念高一档。

## 5.4 一次请求的完整路径(把你的项目串成一条线)

浏览器访问 `http://demo.127.0.0.1.nip.io:9443`,完整发生的事:

```
① nip.io 泛解析:demo.127.0.0.1.nip.io → 127.0.0.1(浏览器以为访问本机)
② SSH 隧道:本机9443的流量经加密隧道 → 服务器上的 127.0.0.1:9443(避开阿里云备案网关——它读不到明文Host头)
③ 宿主机 9443:被 ingress-nginx controller(hostNetwork)监听
④ controller 按 Host 头匹配 Ingress 规则 → 找到 demo Service
⑤ 节点内核的 iptables/IPVS 规则(第4章)把包 DNAT 到某个 demo Pod 的 IP:80
⑥ Pod 里的 nginx 返回页面,原路返回
```

每一步都有对应的排障手段:① `ping demo.127.0.0.1.nip.io` 验证解析;② 隧道断了先重连;③ `ss -tlnp | grep 9443`;④ `kubectl get ingress -A` 看规则;⑤ `kubectl get endpoints -n demo` 看后端是不是空的;⑥ `kubectl logs`。

## 5.5 Calico 与两个你踩过的坑的原理版解释

**Calico 在干什么**:K8s 只定义了 CNI(容器网络接口)标准——"给我把 Pod 网络配好",具体实现交给插件。Calico 的工作:给每个 Pod 分配集群唯一的 IP(100.x 段),并打通**跨节点**的 Pod 通信(通过节点间的路由或隧道【延伸,你未深究】)。没有它,第 3.4 的第 5 步就断,Pod 永远卡在 ContainerCreating。

**坑 1:Calico CRD 时序报错**(`no matches for kind "Installation"`)。CRD(自定义资源定义)是"先教会 K8s 认识一种新资源类型,再创建这种资源"。Calico 用 Operator 方式部署:先注册 CRD,再创建 Installation 等资源。第一次跑时注册还没完成就去建资源 → 报"不认识这个类型"。**重跑就好**,因为第二次 CRD 已存在。原理教训:**声明式系统里,资源之间有创建顺序依赖时,报"类型不存在"先想到 CRD 未就绪,重试通常能过。**

**坑 2:改端口的连环撞车**(8080 被占 → 9443)。ingress-nginx controller 容器**内部**已经占了一组端口(健康检查、webhook 校验等),你把对外的 --http-port 改成 8080 时和它内部的某个监听撞了;8443 同理被 webhook 占用,所以 HTTPS 改 8543。原理教训:**改任何中间件的端口前,先查它内部已占用哪些端口(`--help` 或文档),不要拿"感觉空闲"的端口去试。** 而排查 CrashLoopBackOff 的关键动作你做对了:`kubectl logs --previous`——容器反复重启时,当前日志可能是空的,崩溃前的日志在"上一次"里。

# 第 6 章 数据不能丢:K8s 存储体系

## 6.1 问题:可写层随容器蒸发(第 1 章埋的伏笔)

容器重建 = 可写层蒸发。对无状态网页无所谓,但 **Harbor 的镜像、Gitea 的代码仓库、数据库**这些有状态服务,数据一丢就是灾难。K8s 的答案是:把存储从容器生命周期里**剥离**出来,单独建模。

## 6.2 四个名词:一套"找房"的供需模型

| 名词 | 白话 | 比喻 |
|---|---|---|
| **PV**(PersistentVolume) | 一块实际可用的存储,在集群里"登记在册" | **房源**:真实存在的一间房 |
| **PVC**(PersistentVolumeClaim) | 应用发起的存储申请:"我要 10Gi 可读写" | **求租**:一张需求单 |
| **StorageClass** | 定义"用什么方式造房"的模板,并指定施工队 | **中介 + 建房标准** |
| **Provisioner**(施工队) | 真正去创建存储的家伙(你的是 nfs-subdir-external-provisioner) | 盯着求租单,建房、交房 |

两种供给方式:
- **静态供给**:管理员提前手动建好一批 PV,等 PVC 来认领——房先建好等人租;
- **动态供给**(你的方案):PVC 一提交,StorageClass 指定的 provisioner **自动创建 PV**——中介看到需求单直接盖房。**这就是"动态"二字的含义:存储按需自动创建,不需要人提前准备。**

**默认 StorageClass**(你把 nfs-storage 设为了默认,靠注解 `storageclass.kubernetes.io/is-default-class: "true"`):PVC 不写 storageClassName 时自动用它。好处:应用清单更干净,换存储后端时应用不用改。

## 6.3 动态供给的全链路(你那次 1Gi PVC 实测的内部过程)

```
① 你提交 PVC(1Gi)
② nfs-subdir provisioner(它也是个 Deployment)watch 到新 PVC
③ 它调 K8s API 创建一个 PV 对象,同时在 NFS 服务器上 mkdir 一个子目录
④ PVC 和 PV 绑定 → 状态 Bound
⑤ 之后 Pod 挂载这个 PVC → kubelet 把 NFS 子目录挂进容器
```

你当时的验证:"状态变 Bound,且 /data/nfs 下自动生成对应子目录"——你亲眼看到了第③步的产物。**这也是面试里讲动态存储最有力的一句:"我提交 PVC 后,去 NFS 服务器上看到了自动创建的目录,状态变 Bound。"**

## 6.4 NFS 本身补两分钟课

NFS(网络文件系统)= 把一台机器的目录共享给其他机器挂载,像"网络共享文件夹"。你的服务端配置逐项拆:

```bash
/data/nfs *(rw,sync,no_root_squash,no_subtree_check)
#  ↑共享目录  ↑谁(*=任何人)  ↑读写  ↑写入落盘再返回  ↑客户端root不降权  ↑按子树导出
```

`no_root_squash` 值得停一下:默认情况下 NFS 会把客户端的 root"降权"成普通用户(安全机制,防止客户端 root 冒充);`no_root_squash` 关掉这个保护——客户端的 root 就等于存储上的 root。**学习图方便,生产要意识到这是安全敞口。**另外 NFS 依赖 RPC(所以服务端要起 rpcbind),`exportfs -rv` 是让 /etc/exports 生效,`showmount -e` 是从客户端验证"能看到哪些共享"。

## 6.5 回到你的项目

Harbor(镜像仓库)、Gitea(代码库)、Jenkins(工作区)的 PVC 全走 nfs-storage——所以你删它们的 Pod 重建后,镜像、代码、插件都还在:**数据活在 NFS 上,Pod 死了与数据无关**。反过来这也提示你:Harbor 里 24.86MiB 的镜像、Gitea 里的 demo-app 仓库,物理上都在 ECS 的 `/data/nfs` 目录树下——"K8s 里的数据在哪"这类问题,你现在能一路指到具体目录。

# 第 7 章 Helm:K8s 的包管理器

## 7.1 问题:一个应用二十个 yaml,谁受得了

Harbor 不是一个小东西:core、portal、registry、jobservice、database、redis……每个都是 Deployment + Service + ConfigMap + PVC + Ingress 的组合,加起来**几十个 yaml**。而且它们不是死配置——镜像版本、域名、密码、存储类,不同环境要填不同的值。

手写会疯,手动改会漏。解决方案你其实早已用过:**模板化 + 打包**。这就是 Helm。

## 7.2 Chart = 模板 + 变量

一个 Chart(安装包)里最核心的两样:

- **templates/**:一整套 yaml **模板**——长 yaml 里挖了很多空,写作 `{{ .Values.image.tag }}` 这类占位符(Go 模板语法);
- **values.yaml**:默认**填空答案**。

安装 = 拿变量渲染模板 → 生成完整 yaml → 提交给 K8s。**Helm 本质上是个"填空题生成器 + 安装管理器"。**

**Release 概念**:同一个 Chart 可以安装多份,每一份叫一个 release(用 release 名字区分)——就像同一份装修图纸,可以在不同楼层各装一次。对应命令:`helm install`(初次装修)、`helm upgrade`(改造)、`helm rollback`(回退到上一次装修)。

## 7.3 回到你的项目:那条 install 命令逐参数归位

```bash
helm install harbor harbor/harbor -n harbor --create-namespace \
  --set expose.type=ingress \              # ← 填"暴露方式"这个空:走 Ingress
  --set expose.ingress.className=nginx \   # ← 填"IngressClass"这个空
  --set expose.tls.enabled=false \         # ← 填"要不要证书"这个空:HTTP,省证书
  --set trivy.enabled=false \              # ← 填"漏洞扫描器"这个空:关,省内存
  --set persistence.persistentVolumeClaim.*.storageClass=nfs-storage  # ← 所有 PVC 的空都填 nfs-storage
```

看懂了吗——**你用一条命令,替 Harbor 填了五十张空卷**。如果不用 Helm,这些改动意味着手改几十个 yaml。

**`helm upgrade --reuse-values --set k=v` 的语义**:升级时"沿用上次的全部填空答案,只覆盖指定的几个"。你改域名那次用的就是它——只改 hosts.core 和 externalURL 两个值,其余几十项原样保留。不写 --reuse-values 的话,没指定的项会回落到 chart 默认值,你的定制会被冲掉。

## 7.4 一句话对比 kustomize(面试可能提)【延伸】

kustomize 是另一种思路:不搞模板填空,而是"**基础 yaml + 补丁**"(overlay)——保留原始 yaml,用补丁文件描述差异。Helm 适合复杂应用分装,kustomize 适合"同一套清单的小幅环境差异"。知道区别即可。

# 第 8 章 CI:从代码到镜像

## 8.1 问题:手工构建的痛,你亲身经历过

回想你的 v1→v2:改代码 → 敲 build → 敲 push → 改 yaml → git push。**每一步都是你手敲的**——一次没关系,一天发十次版呢?换三个开发者呢?凌晨两点发版呢?

手工流程的三大死穴:**步骤多必出错**(漏一步就是事故)、**环境不一致**(我的电脑和他电脑构建出的镜像不一样)、**不可追溯**(谁、什么时候、基于哪个 commit 构建的?没人记得)。

**CI(持续集成)** 的定义就从这里来:**代码一提交,自动在标准环境里执行"构建→测试→产出镜像→推入仓库"这条固定流水线**。三个关键词:自动触发、环境标准化、产物入库。

## 8.2 Jenkins 的心智模型

Jenkins 是最老牌的 CI 服务器,概念不多,四个就够:

- **Master(控制器)**:Jenkins 的"大脑"——Web 界面、任务调度、配置管理都在这。你部署的那个 Jenkins Pod 就是 Master。
- **Agent(节点)**:真正干活的"工人"。Master 把构建任务派给 agent 执行(小团队常 Master 自己兼跑,你的场景就是)。【延伸:分布式 agent 你没配,知道概念】
- **Job(任务)**:一次构建的定义。老式是界面上点出来的"自由风格任务";现代写法是 **Pipeline as Code**——把流水线写成一个 `Jenkinsfile` 文件放进代码仓库,和代码一起版本化。
- **Workspace(工作区)**:每次构建的现场——代码 checkout 到哪、构建产物在哪。你的 PVC 20Gi 存的就是这些。

**为什么 "Pipeline as Code" 是革命**:流水线定义进了 Git,就有了版本、评审、回滚——CI 配置本身也被 GitOps 化了。

## 8.3 Jenkinsfile 语法精讲(你的最弱项,放慢)

Declarative Pipeline(声明式流水线)骨架,给你项目量身写的完整版:

```groovy
pipeline {
    agent any                        // 在哪个 agent 上跑(any=任意可用节点)

    environment {                    // 全局环境变量,后面所有 stage 可用
        HARBOR = 'harbor.127.0.0.1.nip.io:9443'
        IMAGE  = 'harbor.127.0.0.1.nip.io:9443/devops/demo'
        TAG    = "v${BUILD_NUMBER}"   // BUILD_NUMBER 是 Jenkins 内置变量,每次构建自动+1
    }

    stages {
        stage('拉代码') {
            steps {
                git url: 'http://gitea.devops.svc.cluster.local:3000/gitea/demo-app.git', branch: 'main'
            }
        }
        stage('构建镜像') {
            steps {
                sh "nerdctl build -t ${IMAGE}:${TAG} . --insecure-registry"
            }
        }
        stage('推送仓库') {
            steps {
                sh "nerdctl push ${IMAGE}:${TAG} --insecure-registry"
            }
        }
        stage('更新部署清单') {       // GitOps 的关键一步:改 Git 里的 tag
            steps {
                sh "sed -i 's|${IMAGE}:.*|${IMAGE}:${TAG}|' deploy/deployment.yaml"
                sh "git commit -am 'ci: ${TAG}' && git push"
            }
        }
    }

    post {                           // 收尾:无论成败都执行
        success { echo '流水线成功 ✅' }
        failure { echo '流水线失败 ❌,看上方日志' }
    }
}
```

逐层记:**pipeline(整条线)→ agent(在哪跑)→ stages(分几步)→ stage(每步)→ steps(具体动作)→ sh(执行 shell 命令)**。读别人 Jenkinsfile 的技巧:只看 stage 名字就能讲出这条线干什么,细节都在 steps 里。

这个 Jenkinsfile 和你手动做的事**一字不差**,只是全部写成了代码——这就是"你已经会 CI,只差把它写下来"。

## 8.4 Webhook:从"猫眼看人"到"门铃"

代码提交后 Jenkins 怎么知道?

- **轮询**:Jenkins 每隔 N 分钟问一次 Gitea"有新提交吗"——像从猫眼往外看,浪费且延迟大;
- **Webhook**:Gitea 在收到 push 时,**主动向预先登记的 URL 发一个 HTTP POST**(带仓库、分支、commit 信息)——像按门铃,事件驱动,即时触发。

配置路径(你未实操,【规划】口径):Gitea 仓库 → 设置 → Webhooks → 添加,URL 填 Jenkins 的 hook 端点(装了 Git 插件后是 `http://<jenkins>/github-webhook/` 或 generic hook),触发事件选 push。ArgoCD 的 3 分钟轮询也一样可以配 Gitea webhook 加速——**两家都是同一个原理:HTTP 回调**。

## 8.5 kaniko:集群内构建为什么不用 Docker【延伸/规划】

接全自动 CI 时构建这步有个坑:Jenkins 容器里要 build 镜像,传统做法是"挂载宿主机 docker.sock"——等于把宿主机 root 权限交给构建过程,又危险又依赖 Docker。**kaniko** 的思路:完全在用户态逐层解包基础镜像、执行 Dockerfile 指令、重新打包推走,**全程不需要 Docker 守护进程、不需要特权**,直接以一个 Job 的形式在集群里跑。这就是你规划里"用 kaniko 替换手动 nerdctl build"的原因——面试讲出"为什么不用 Docker 构建"是加分点。

## 8.6 回到你的项目:你离全自动差哪三根线

诚实现状:Jenkins 部署了(跳过了插件安装),CI 的核心动作(构建+推送)**手动**执行过,git 变更后的自动部署(CD)**已经全自动**。差的三根线:

1. **插件**:Jenkins 离线没装 git/credentials 等插件 → 配国内插件源或离线导入;
2. **Jenkinsfile**:把 8.3 的文件放进 demo-app 仓库(内容你已会写);
3. **Webhook**:Gitea → Jenkins 的门铃。

接上后:git push → 门铃响 → Jenkins 拉代码构建推镜像 → 改 tag 推回 Git → ArgoCD 同步上线,**全链路无人工**。这三根线就是你"下一步要做的事",面试讲得出每根线怎么接,半自动就不丢人。

# 第 9 章 CD 与 GitOps:从镜像到线上(ArgoCD)

## 9.1 交付的两种流派:push 与 pull

镜像进了 Harbor,最后一步是"让集群跑起新版本"。两种做法:

- **Push 流**:Jenkins(或人)拿着集群凭证,从外面 `kubectl apply` 把变更**推进**集群。问题:CI 系统要持有生产集群的 root 级凭证(大安全隐患);谁来apply、改了什么,分散在各个系统里,难对账。
- **Pull 流**(GitOps):集群里住着一个组件(ArgoCD),它**自己盯着 Git 仓库**,发现"Git 里的期望状态"和"集群实际状态"不一致,就自动把集群**拉向** Git 声明的样子。集群凭证不出集群,Git 是唯一真相源。

**K8s 时代 pull 流胜出的根本原因**:K8s 本来就是声明式 API——"集群状态应等于某份声明"是它的母语,GitOps 只是把"那份声明"从散落各处收拢到 Git 一个地方。

## 9.2 GitOps 四原则(面试标准答案的原理版)

1. **声明式**:整套期望状态用声明描述(yaml),不是脚本;
2. **版本化、不可变**:期望状态存在 Git 里,任何变更是 commit,历史可追溯、可回滚;
3. **自动拉取**:agent 自动从 Git 拉取期望,人不碰集群;
4. **持续对账**:agent 不停对比期望与实际,漂移自动纠正(或至少告警)。

发现没有——**GitOps 就是第 3.2 的控制循环,把"期望状态"从 etcd 里的对象扩展到了 Git 仓库**。你学 K8s 的那把钥匙,直接解锁 ArgoCD。

## 9.3 ArgoCD 拆解

**它是什么**:跑在你集群里的一组 Pod(UI + API + 若干控制器)。核心是一个自定义资源 **Application**——对,ArgoCD 用 K8s 的方式管理部署:你 `kubectl apply` 一个 Application 清单,ArgoCD 的控制器就接管了它,进入控制循环。

**Application 字段逐个讲**(你配的那份):

```yaml
spec:
  source:                          # 期望状态从哪来
    repoURL: http://gitea.devops.svc.cluster.local:3000/gitea/demo-app.git
    path: deploy                   # 只盯这个目录(deploy/ 里是 K8s 清单)
  destination:                     # 同步到哪
    server: https://kubernetes.default.svc    # "本集群"(集群内 Service DNS)
    namespace: demo
  syncPolicy:
    automated: { selfHeal: true }  # 自动同步 + 漂移自愈
    syncOptions: [ CreateNamespace=true ]   # namespace 不存在就建
```

**repoURL 为什么必须用集群内 Service DNS**:`127.0.0.1.nip.io` 是给**你的浏览器+SSH隧道**用的(解析到你的电脑 127.0.0.1,再走隧道)。而 ArgoCD 的控制器跑在集群的 Pod 里——Pod 里解析 `127.0.0.1.nip.io` 得到 127.0.0.1,**指的是它自己这个 Pod**,当然连不上 Gitea。集群内部互访要用 K8s 的服务发现:`gitea.devops.svc.cluster.local`(由 coredns 解析,格式是"服务名.namespace名.svc.cluster.local")。**同一个地址,视角不同,含义不同——这是本教程最值得吃透的细节之一。**

**对账循环的状态机**(你界面看到的每个词的准确定义):

```
fetch Git 清单 ──► 与集群实际做 diff ──► 状态:
                                      ├─ 一致 → Synced + Healthy(你看到的最终状态)
                                      └─ 不一致 → OutOfSync → 自动 apply → Progressing → 复查
```

- **默认每 3 分钟轮询**一次 Git;你 `patch` 加 refresh 注解 = 喊一嗓子"现在就去查",不用等 3 分钟。配了 Gitea webhook 则推送时立刻触发。
- **selfHeal**:有人绕过 Git 手动改了集群(比如 kubectl scale)→ ArgoCD 发现实际与 Git 不符 → **自动改回来**。这就是"防漂移"。
- **prune**(你没开):Git 里删了某资源 → 集群里也删。开了才是完整镜像语义,不敢开就手动管控,知道取舍即可。【延伸】
- **回滚 = git revert**:把 Git 的 deployment.yaml tag 从 v2 改回 v1 并提交 → ArgoCD 发现 Git 变了 → 自动把集群滚回 v1。**注意方向:不回滚集群,而是回滚 Git**——因为 Git 才是真相源。这就是"易回滚"的原理。

**--insecure 的原因**:你的入口(Ingress)走 HTTP,浏览器 → Ingress → ArgoCD server 这段没有 TLS;而 ArgoCD server 默认自己启用 HTTPS。协议对不上浏览器就报 SSL 错误。加 `--insecure` = 让 server 内部也走 HTTP,TLS 终止点交给未来的 Ingress 层。**原则:入口协议和组件协议要对齐,并清楚 TLS 到底终止在哪一跳。**

## 9.4 完整传记:v1→v2 那天,ArgoCD 内部发生了什么

1. 你 `sed` 改了 Git 里 deployment.yaml 的 tag → `git push`;
2. ArgoCD 控制器(轮询或你 patch 的 refresh)拉取 deploy/ 目录,渲染出"期望状态";
3. 和集群实际 diff:发现实际 Pod 镜像还是 v1 → **OutOfSync**;
4. syncPolicy.automated 触发 → 对集群执行 apply(和 kubectl apply 走同样的 API Server 通道);
5. Deployment 控制器创建新 RS → 滚动更新(第 4 章)→ kubelet 从 Harbor 拉 v2 镜像(仓库地址在 containerd 的 certs.d 里被信任,第 2 章);
6. 新 Pod Ready,旧 Pod 终止 → ArgoCD 复查 diff 归零 → **Synced + Healthy**;
7. 你刷新浏览器,页面从 v1 变 v2。

七步里,1-3 是 GitOps 循环,4-5 是 K8s 控制循环,**两个循环咬合在一起**——这就是整套系统的全部秘密。

# 第 10 章 中间件三兄弟的定位与选型(短章)

## 10.1 Gitea:Git 服务器的本质

Git 本身是分布式的,仓库只是"一个目录 + 完整历史"。Gitea 做的事:托管裸仓库(bare repo)+ 提供 HTTP/SSH 拉推服务 + Web 界面(评审、权限、issue)。**它与 GitHub 是同类,区别只在"跑在谁的服务器上"**——代码不出内网。选型对比:

| | Gitea | GitLab | GitHub |
|---|---|---|---|
| 资源占用 | 几百 MB(SQLite 就够) | 好 several GB,要独立 PG | 公网 SaaS |
| 适合 | 小团队自建、学习 | 中大企业(自带 CI/审批流) | 开源/跨公司协作 |
| 你的理由 | 单节点省内存 | 教程生产版用,你裁掉了 | 代码不能出内网 |

你用 Gitea API 建仓库、su 到 git 用户建管理员(1.22 禁 root)——两个细节在《防问倒手册》里是防伪细节,这里你知道了"为什么":Gitea 容器内以 git 用户运行,程序拒绝 root 身份执行管理命令,是安全设计。

## 10.2 Harbor:Docker Registry 的企业壳

底层存储镜像的就是一个标准 **Docker Registry**(存 blob 分层 + manifest 清单),Harbor 在它外面套了一层企业能力:**认证鉴权(RBAC)、项目隔离、Web UI、审计、漏洞扫描(trivy)、垃圾回收(GC)、多仓库复制**。

两个有意思的机制(面试聊到 Harbor 深一层时用):
- **镜像在磁盘上的形态**:一个镜像 = manifest(清单)+ 若干 layer blob。**分层去重**:两个镜像共享基础层,磁盘只存一份——这就是 Harbor 界面里"镜像大小 24.86MiB"和实际占用不完全相等的原因;
- **公开/私有**:私有项目拉取要认证,K8s 侧要建 docker-registry 类型的 Secret 并配 imagePullSecrets;你设了公开,省掉这一步——**面试主动说"我为了省 imagePullSecret 设了公开,生产会设私有+Secret"**,取舍意识就有了。

## 10.3 CI 工具对比一句话

Jenkins(老牌,插件生态最全,Master/Agent 要自己养)/ GitLab CI(和 GitLab 一体,.gitlab-ci.yml)/ GitHub Actions(云端,生态爆发)。你简历场景讲:"我装的 Jenkins,知道它和 GitLab CI 的差异;概念相通,换工具是学语法不是学思想。"

# 第 11 章 全链路串讲:一次发布的完整传记(最重要的一章)

前面 10 章是单词,这一章是文章。**面试的最高形态就是让你"从头讲一遍项目"**——下面这段传记,每个括号标注该步骤用的是第几章的知识。练到能脱稿讲 3 分钟。

## 11.1 一次发布的完整传记

> 开发者改了 `index.html`,git push 到 **Gitea**(第10章:Git 服务器)。此刻集群里谁都不知道。
>
> 【当前版本:人工接手】我用 **buildkit**(第8章:构建引擎)构建新镜像——`nerdctl build` 走 buildkit,基础镜像 `nginx:alpine` 从 containerd 配置的国内 mirror 拉(第2章),产物分层落盘(第1章),然后 `nerdctl push` 推进 **Harbor**(第10章)——这条推送之所以能通,是因为 containerd 的 certs.d 里显式信任了这个 HTTP 仓库(第2章)。
>
> 接着我改 Git 里 `deploy/deployment.yaml` 的镜像 tag 并 push——**这是全链路唯一"仪式性"的人工动作:宣告期望状态已变更**。
>
> 【全自动部分开始】**ArgoCD**(第9章)轮询/被 refresh 唤醒,拉取 deploy/ 目录,与集群实际 diff → OutOfSync → 执行 apply。请求进入 **API Server**(第3章)→ 写入 **etcd** → **Deployment 控制器**创建新 ReplicaSet → **Scheduler** 绑节点 → **kubelet** 调 **containerd** 从 Harbor 拉新镜像(第2章)→ 创建容器:namespace/cgroups 隔离(第1章)、**Calico**(第5章)分 IP、PVC 挂载(第6章,若需存储)。
>
> 新 Pod Ready 后,滚动更新摘除旧 Pod(第4章)。用户浏览器访问 `demo.127.0.0.1.nip.io:9443` → nip.io 解析 → SSH 隧道(第5章)→ **ingress-nginx**(第5章)按 Host 转发 → Service 的 iptables 规则 DNAT(第4章)→ Pod 返回 v2 页面。ArgoCD 复查 diff 归零 → **Synced + Healthy**(第9章)。
>
> 【规划版本:全自動】git push 同时触发 **Gitea Webhook**(第8章)→ **Jenkins** 执行 **Jenkinsfile**(第8章):拉代码 → **kaniko** 集群内构建(第8章)→ 推 Harbor → sed 改 tag 推回 Git → 后半段与上面完全相同。人从"操作员"变成"旁观者"。

**这段传记的威力**:面试官从任何一环打断追问,你都能就地展开对应章节;讲完不打断,它本身就是 3 分钟的完美项目陈述。

# 第 12 章 WAF 项目技术课(串联版,你基础好,压缩讲)

## 12.1 HTTP 全链路复习(你的老底,串起来)

"输入网址到看到页面":浏览器缓存 → hosts/DNS 解析(先 hosts——你在本地双 WAF 就靠它;再递归查询运营商 DNS,迭代获取最终答案)→ TCP 三次握手 → TLS 握手(若 HTTPS)→ 发 HTTP 请求 → 服务器层层处理 → 响应渲染。你的 WAF 项目,就是在"发 HTTP 请求"和"服务器处理"之间插了一道安检;CDN/OSS 则改写了"资源从哪来"。

## 12.2 WAF:反向代理 + 检测管线

- **反向代理**(对照正向):正向代理替**客户端**出门(隐藏客户端);反向代理替**服务器**接客(隐藏后端)。WAF 是后者——DNS 把域名指到 WAF,所有流量必经它。
- **检测管线**:请求进来 → 解析(method/URI/头/体)→ 规则与语义分析(SQL 注入特征、XSS payload、路径遍历)→ 动作(放行转发 / 拦截返回 / 人机验证)。你实测的 `?id=phpinfo();system('id')` 命中规则 → 拦截页 + 拦截 ID,面板计数+1。
- **为什么独立部署四条**(影响范围/端口冲突/资源隔离/故障隔离)——你在实践里用 80 端口冲突亲身验证了第二条。

## 12.3 TLS 与 SSL 卸载

握手原理(面试口述版):客户端发随机数+支持的套件 → 服务端回证书(**证书链**:根 CA → 中间 CA → 你的站点证书,浏览器沿链验签到内置的根)→ 客户端验证后用证书公钥加密一个预主密钥 → 双方算出对称会话密钥 → 之后全部走对称加密。**非对称只用于握手,数据传输是对称加密**——所以"SSL 卸载"才有意义:把握手和解密放在 WAF 这一层做(443 进),WAF 到后端走 HTTP(8080),后端省掉加解密开销,证书统一在一处管理。安全前提:后端只监听 127.0.0.1,那段明文不出机器。

## 12.4 CDN + OSS:静态资源的另一条路

- **DNS 的 CNAME 链**:img.chenshihao.cn → CNAME → CDN 调度域名 → 解析到**离用户最近的边缘节点**。边缘有缓存直接返回;没有则**回源**到 OSS 拉取并缓存。收益:快(就近)+ 省 OSS 流量费 + 源站不暴露。
- **OSS 对象存储**:扁平的"桶-对象"模型(无目录树),HTTP API 访问。**Referer 防盗链**:浏览器请求资源时自动带 Referer 头(来源页),OSS 校验白名单,不匹配返回 AccessDenied;空 Referer 拒绝防直接开 URL。**你实测过两头:白名单外被拒、站内引用正常**。知道边界:Referer 可伪造(curl -e),更强的是带时效的签名 URL【延伸】。
- **你留下的经典问题**:CDN 回源时 Referer 是 CDN 节点的,不在 OSS 白名单 → 403。生产解法:OSS 白名单加 CDN 回源 Referer,或改用 URL 鉴权。你能讲出"为什么会发生"(回源请求的 Referer 变了),就已超过背答案的人。

## 12.5 两个项目的一次对照(面试联动题)

- 都踩了**ICP 备案拦截**:WAF 项目发现"HTTPS 能过"(拦截只读明文 Host 头);DevOps 项目发现"改端口没用"(依据是 Host 不是端口),最终 SSH 隧道把整个 HTTP 封进加密通道。两次绕法不同,但原理同一句:**拦截规则依据的维度,决定绕过思路**。
- 架构哲学对照:WAF 项目是**传统架构**(裸 Nginx/代理 + 云产品组合),DevOps 项目是**云原生架构**(声明式 + 控制循环 + 自动对账)。你能讲清"从手写 nginx.conf 到 Ingress 对象、从手动部署到 GitOps"的演进逻辑,就拿到了两个项目之间的叙事线。
