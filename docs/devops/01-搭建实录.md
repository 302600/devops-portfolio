## 一、项目背景与目标

- **目的**：给简历补一个真正对口运维岗的云原生项目，替代分量不足的 Spark 毕设项目。运维岗看重的是 Linux、容器、K8s、CI/CD 这套东西，Spark 那个偏大数据开发，聊起来对不上岗位，所以要换一个真正"运维味"的项目。
- **原则**：真搭真懂，不抄结果。每一步都先理解原理再执行，遇到报错自己查、自己解决，这样面试才敢展开讲。
- **参考教程**：付费课程"运维导航"的云原生 DevOps 项目（原版是**多地多中心架构**，规模很大）。本项目做**单机最小可用版裁剪**——用一台云服务器把整条流水线跑通，先把原理和链路搞明白，成本也能控制住。
- **目标链路**（这条链路就是整个项目的主线，面试一定要能背下来）：

```
开发提交代码 → GitLab / Gitea → Jenkins 构建镜像 → Harbor 镜像仓库 → ArgoCD 部署 → K8s 运行
                                                                （可选）+ Prometheus + Grafana 监控
```

一句话理解：**代码从提交到最终在 K8s 上跑起来，全自动，不用人工手动部署**，这就是"云原生 DevOps 流水线"要解决的事。

## 三、已完成的操作步骤（按时间顺序）

> 每一步都写清"做了什么 + 为什么这么做 + 关键命令"。

1. **购买 ECS**
   - 做了什么：先把计费模式从"包年包月"改成"**按量付费**"；镜像选 Rocky Linux 10.2；勾选"分配公网 IPv4"；带宽按流量 5M；安全组放行 22 端口；设置 root 自定义密码。
   - 为什么：学习用只需要几天，按量付费用完就释放最省钱；放行 22 是为了能 SSH 登录。

2. **连接服务器**
   - 做了什么：用阿里云控制台的"远程连接"（Workbench）以 root 登录。
   - 为什么：还没配好本地 SSH 客户端时，控制台自带的网页终端最省事，也不怕把自己锁在外面。

3. **关闭防火墙与 SELinux**
   - 关键命令：
     ```bash
     systemctl stop firewalld
     systemctl disable firewalld
     setenforce 0
     sed -i 's/^SELINUX=enforcing/SELINUX=disabled/' /etc/selinux/config
     getenforce
     ```
   - 为什么：K8s 组件之间端口通信很多，本机防火墙和 SELinux 会拦，学习环境先关掉减少干扰（真正的第一道门是云安全组）。
   - 结果：镜像自带 SELinux 已经是 Disabled。

4. **跳过教程的"配置静态 IP"**
   - 做了什么：**直接跳过这一章**。
   - 为什么：云服务器的 IP 是平台固定分配的，手动去改静态 IP 很可能导致 SSH 断连，把自己锁在服务器外面。照教程做之前要先判断"环境差异"。

5. **刷新软件源缓存并装基础工具**
   - 关键命令：
     ```bash
     dnf clean all
     dnf makecache
     dnf install -y net-tools vim wget tar
     ```
   - 为什么：先把源缓存刷新，保证后面装包能找到；net-tools/vim/wget/tar 是日常必备工具。

6. **装容器 / K8s 底层网络依赖**
   - 关键命令：
     ```bash
     dnf install -y iptables iptables-nft iproute-tc conntrack-tools socat
     ```
   - 为什么：K8s 的网络（Service 转发、Pod 通信、连接跟踪）底层依赖这些工具，缺了后面装集群会报错。

7. **安装 Docker**
   - 做了什么：Docker 官方源在国内不可用，改用**阿里云镜像源**（写 `/etc/yum.repos.d/docker-ce.repo`，baseurl 指向 `mirrors.aliyun.com/docker-ce/linux/centos/9/$basearch/stable`），然后安装：
     ```bash
     dnf install -y docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin
     systemctl enable --now docker
     ```
   - 为什么：先用 Docker 验证容器环境能不能跑通；官方源连不上就换国内镜像源。

8. **配置 Docker 镜像加速**
   - 做了什么：写 `/etc/docker/daemon.json` 的 `registry-mirrors`，然后重载重启：
     ```bash
     systemctl daemon-reload
     systemctl restart docker
     ```
   - 结果：最终用 `docker.m.daocloud.io` / `docker.nju.edu.cn` / `mirror.baidubce.com` 成功；`docker run hello-world` 输出 **Hello from Docker!** 验证通过。
   - 为什么：直接从 Docker Hub 拉镜像国内又慢又容易失败，配加速器（拉取代理）能大幅提速。

9. **学习教程第二章（纯理论）**
   - 做了什么：看多地多中心架构图、命名规范，并把这套规范**裁剪映射到本项目**（就是上面第二节的规划命名）。
   - 为什么：理论先过一遍，动手时才知道每个命名、每个环境是干嘛的。

10. **第三章开始：设置主机名 + 写 hosts**
    - 关键命令：
      ```bash
      hostnamectl set-hostname k8s-master01-172-17-175-55
      echo "172.17.175.55 k8s-master01-172-17-175-55" >> /etc/hosts
      ```
    - 为什么：K8s 节点靠主机名标识，主机名必须唯一而且能被解析，否则集群起不来。

11. **确认时间同步**
    - 关键命令：`chronyc sources`
    - 结果：Rocky 10.2 自带 chrony，已同步到阿里云内网 NTP（100.100.x.x）。
    - 为什么：K8s 组件之间要用证书校验，时间偏差太大集群会起不来，所以时间同步很关键。

12. **安装 Sealos**
    - 做了什么：绕开 GitHub，改用官方 RPM 仓库（写 `/etc/yum.repos.d/labring.repo`，`baseurl=https://yum.fury.io/labring/`），然后：
      ```bash
      dnf install -y sealos
      ```
    - 结果：版本 5.1.1。
    - 为什么：GitHub 下载不稳定，用官方 RPM 源更靠谱。Sealos 是一键部署 K8s 的工具。

13. **安装 tmux 并在会话里跑长任务**
    - 关键命令：
      ```bash
      dnf install -y tmux
      tmux new -s k8s
      tmux attach -t k8s
      ```
    - 为什么：装 K8s 是长任务，网页终端一断连任务就被杀了；放 tmux 会话里跑，断线也不会中断。

14. **执行 `sealos run` 装单节点 K8s → 报 containerd 冲突**
    - 做了什么：装 kubernetes v1.31.9 + helm v4.0.1 + calico v3.28.1，只写 `--masters 内网IP`，不写 `--nodes`（因为是单节点）。
    - 结果：**报 containerd 冲突**（原因见踩坑第 7 条）。

15. **卸载 Docker 与 containerd 给 Sealos 让路**
    - 做了什么：停服务、`dnf remove` docker 相关包、清理残留目录：
      ```bash
      systemctl stop docker containerd
      dnf remove -y docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin
      rm -rf /var/lib/docker /var/lib/containerd /etc/containerd
      ```
    - 为什么：Sealos 要自己安装并管理 containerd，不肯复用已有的；同一台机上两套 containerd 会冲突。

16. **重新执行 `sealos run` 完成单节点 K8s 安装（成功）**
    - 做了什么：装 Kubernetes v1.31.9 + Helm v4.0.1 + Calico v3.28.1，只指定 `--masters 172.17.175.55`，不写 `--nodes`（单节点，master 兼 node）。安装过程中 Sealos 会要求输入集群名 `k8s-master01-172-17-175-55` 做确认。
    - 关键命令：
      ```bash
      sealos run labring/kubernetes:v1.31.9 labring/helm:v4.0.1 labring/calico:v3.28.1 --masters 172.17.175.55
      ```
    - 为什么：单节点没有额外 node，只声明 master 即可；集群名确认是防止误装。

17. **验证集群组件全部就绪**
    - 关键命令：
      ```bash
      kubectl get nodes
      kubectl get pod -A
      ```
    - 结果：`kubectl get nodes` 节点 Ready；`kubectl get pod -A` 全部 Running，包括 etcd、kube-apiserver、kube-controller-manager、kube-scheduler、kube-proxy、coredns×2、calico-node、calico-typha、calico-kube-controllers、calico-apiserver×2、csi-node-driver、tigera-operator。
    - 为什么：先确认控制面 + 网络插件都健康，再往上装东西才不会踩到底层问题。

18. **检查并确认 master 污点已自动去除**
    - 关键命令：
      ```bash
      kubectl describe node k8s-master01-172-17-175-55 | grep -i taint
      ```
    - 结果：`Taints: <none>`。Sealos 已自动去除 control-plane 污点，**无需手动 taint 操作**。
    - 为什么：单节点集群若保留 master 污点，业务 Pod 会一直 Pending；Sealos 已帮我们处理好了。

19. **安装 nerdctl v2.3.3**
    - 做了什么：通过 GitHub 代理 `https://ghfast.top/` 下载 tar 包，解压后放到 `/usr/local/bin/`。
    - 结果：`nerdctl version` 显示 client v2.3.3、containerd v1.7.27、runc 1.2.6。
    - 为什么：K8s 弃用 docker 后，节点上排查容器用 nerdctl，用法接近 docker；GitHub 直连慢，用代理下载。

20. **配置 nerdctl（对接 containerd 的 k8s.io 命名空间）**
    - 做了什么：写 `/etc/nerdctl/nerdctl.toml`，关键参数：
      ```toml
      namespace = "k8s.io"
      address = "unix:///var/run/containerd/containerd.sock"
      cgroup_manager = "systemd"
      ```
    - 为什么：K8s 的镜像都在 containerd 的 `k8s.io` 命名空间，不配这个 `nerdctl images` 看不到集群镜像。

21. **确认 containerd 已启用镜像加速配置路径**
    - 关键命令：
      ```bash
      grep -n 'config_path' /etc/containerd/config.toml
      ```
    - 结果：输出 `config_path = "/etc/containerd/certs.d"`。
    - 为什么：确认 containerd 会读 certs.d 目录下的 mirror 配置，后面加速配置才会生效。

22. **配置 containerd 镜像加速（多 mirror 故障转移）**
    - 做了什么：创建 `/etc/containerd/certs.d/docker.io/hosts.toml`，列出多个国内 mirror 做故障转移。最终保留有效的 `docker.m.daocloud.io`、`docker.1ms.run`、`docker.xuanyuan.me`；剔除已失效的 `docker.mirrors.ustc.edu.cn`、返回 403 的 `docker.nju.edu.cn`、域名解析失败的 `mirror.baidubce.com`。
    - 关键命令：`systemctl restart containerd`
    - 为什么：containerd 的加速走 certs.d 下的 hosts.toml，多个 mirror 按顺序尝试、失败自动切换。

23. **验证集群可正常拉镜像并跑 Pod**
    - 关键命令：
      ```bash
      nerdctl pull nginx:alpine
      kubectl create deployment nginx-test --image=nginx:alpine
      ```
    - 结果：`nerdctl pull` 成功（12.6 秒 / 25MB）；Pod Running 并获得 Calico 网段 IP `100.82.50.71`。验证后删除该 deployment。
    - 为什么：从「拉镜像」到「起 Pod 拿到网络 IP」全链路走通，才算集群真正可用。

24. **安装 NFS 服务端**
    - 关键命令：
      ```bash
      dnf install -y nfs-utils
      mkdir -p /data/nfs
      echo '/data/nfs *(rw,sync,no_root_squash,no_subtree_check)' >> /etc/exports
      systemctl enable --now rpcbind nfs-server
      exportfs -rv
      showmount -e 172.17.175.55
      ```
    - 为什么：K8s 动态存储要有底层存储，用 NFS 最简单；`exportfs -rv` 让共享配置生效，`showmount` 验证已导出。

25. **部署 NFS 动态存储制备器**
    - 做了什么：编写 `/root/nfs-provisioner.yaml`（Namespace + ServiceAccount + ClusterRole/Binding + Role/Binding + Deployment + StorageClass）。StorageClass 名为 `nfs-storage` 并设为默认（注解 `storageclass.kubernetes.io/is-default-class: "true"`），provisioner 为 `k8s-sigs.io/nfs-subdir-external-provisioner`。
    - 验证方式：创建一个 1Gi 的测试 PVC，状态变 `Bound`，且 `/data/nfs` 下自动生成对应子目录。
    - 为什么：有了默认 StorageClass，应用只要提交 PVC 就能自动分配 PV，不用手动建。

26. **部署 Ingress-nginx v1.11.3**
    - 做了什么：Helm 仓库 kubernetes.github.io 国内不通，改为通过 `ghfast.top` 代理下载官方 baremetal 版 `deploy.yaml`。用 `sed` 把 `registry.k8s.io` 的镜像替换为 `dyrnq/ingress-nginx-controller:v1.11.3` 与 `dyrnq/ingress-nginx-kube-webhook-certgen:v1.4.4`（替换时需去掉 `@sha256` digest）。apply 后再 patch 成 `hostNetwork: true` + `dnsPolicy: ClusterFirstWithHostNet`，让 Ingress 直接占用宿主机 80/443。另外在阿里云安全组放行了 80、443 端口。
    - 结果：controller Pod IP 等于节点 IP `172.17.175.55`；`curl -I http://172.17.175.55` 返回 **404**（说明 nginx 已接管请求但暂无路由规则）。
    - 为什么：单节点没有 LoadBalancer，用 hostNetwork 让 Ingress 直接占宿主机端口，外网可直连。

27. **获取 Harbor Helm Chart**
    - 做了什么：通过 Helm 官方仓库获取 Harbor Chart。
    - 关键命令：
      ```bash
      helm repo add harbor https://helm.goharbor.io
      ```
    - 结果：这个仓库国内可正常访问；chart 版本 **1.19.2** / Harbor 应用版本 **2.15.2**。
    - 为什么：Harbor 组件多，用 Helm 打包安装最省事，先确认仓库能连上再装。

28. **安装 Harbor（单机自包含版，对教程做裁剪）**
    - 做了什么：安装 Harbor 到独立 namespace，走单机自包含方案。
    - 关键命令：
      ```bash
      helm install harbor harbor/harbor -n harbor --create-namespace
      ```
    - 关键参数：`expose.type=ingress`、`expose.ingress.className=nginx`、`expose.tls.enabled=false`（走 HTTP 省掉证书）、各组件 `persistence.persistentVolumeClaim.*.storageClass=nfs-storage`（用前面搭好的 NFS 动态存储）、`trivy.enabled=false`（关闭漏洞扫描组件省内存）、`harborAdminPassword=Harbor12345`。
    - 裁剪对照：教程用**外部 PostgreSQL / Redis / MinIO(S3) / 自签证书 / PowerDNS**（生产级外部依赖）；我们用 **chart 内置 PostgreSQL + Redis、NFS 存储、HTTP、nip.io 泛解析**。
    - 为什么：16G 单机资源有限，自包含 + 关掉可选组件能把内存压下来，先把仓库跑通。

29. **等待并验证 Harbor 启动**
    - 关键命令：
      ```bash
      kubectl -n harbor get pod
      ```
    - 结果：最终 harbor-core、harbor-database、harbor-jobservice、harbor-portal、harbor-redis 均 **1/1**，harbor-registry **2/2**，全部 Running。
    - 为什么：组件都 Ready 才算装成功，再往后配访问和推镜像。

30. **排查并修改 Ingress 端口（80 → 9443）**
    - 做了什么：因备案问题需要把入口从 80 改到非标端口。先尝试 8080 失败（日志报 `port 8080 is already in use`，8080 被 ingress-nginx 容器内部占用），最终改为 **9443**（安全组已放行）。做法是 patch deployment 替换整个 args 数组，追加 `--http-port=9443`、`--https-port=8543`，并把 `containers[0].ports[0].containerPort` 改为 9443。
    - 验证：`ss -tlnp | grep 9443` 有 nginx 监听、`curl -I` 返回 **200**。
    - 为什么：备案拦截作用在标准 HTTP 端口链路上，换非标端口是绕行尝试的第一步。

31. **用 SSH 隧道 + 127.0.0.1 泛解析绕过 ICP 备案拦截**
    - 做了什么：把访问域名换成解析到本机回环地址的 `harbor.127.0.0.1.nip.io`（nip.io 泛解析，`ping` 可确认解析为 127.0.0.1），再在本地电脑通过 SSH 端口转发访问。
    - 关键命令：
      ```bash
      ssh -L 9443:127.0.0.1:9443 root@<公网IP>   # 也可用 ssh -fNL 后台运行
      helm upgrade harbor harbor/harbor -n harbor --reuse-values \
        --set expose.ingress.hosts.core=harbor.127.0.0.1.nip.io \
        --set externalURL=http://harbor.127.0.0.1.nip.io:9443
      ```
    - 为什么：HTTP 流量封装在 SSH 加密隧道内，阿里云网关无法读取 Host 头，因此不触发备案校验。

32. **配置 containerd 信任 HTTP 私有仓库**
    - 做了什么：创建目录 `/etc/containerd/certs.d/harbor.127.0.0.1.nip.io:9443/`（**目录名必须包含端口**），写 hosts.toml 指定 `server = "http://..."`、`capabilities = ["pull","resolve","push"]`、`skip_verify = true`，然后重启 containerd。
    - 关键命令：`systemctl restart containerd`
    - 为什么：HTTP 私有仓库默认不被信任，必须显式声明 `skip_verify` 才能拉/推。

33. **推送镜像验证 Harbor 可用**
    - 做了什么：Harbor UI 新建项目 `devops`（访问级别设为**公开**，这样 K8s 拉镜像无需额外配置 imagePullSecret），然后登录、打标签、推送。
    - 关键命令：
      ```bash
      nerdctl login --insecure-registry harbor.127.0.0.1.nip.io:9443
      nerdctl tag nginx:alpine harbor.127.0.0.1.nip.io:9443/devops/nginx:v1
      nerdctl push harbor.127.0.0.1.nip.io:9443/devops/nginx:v1
      ```
    - 结果：Harbor 界面确认 `devops/nginx` 仓库出现 **v1** 标签、大小 **24.86MiB**，推送成功。
    - 为什么：能从节点推镜像到 Harbor，才算私有仓库真正可用，为后面 CI/CD 打基础。

34. **部署 Gitea 代码仓库**
    - 做了什么：在 namespace `devops` 用 Deployment 部署 `gitea/gitea:1.22.6`，数据库用 SQLite 内置库（省资源），PVC 走 `nfs-storage`，Ingress host 为 `gitea.127.0.0.1.nip.io`。
    - 关键命令（创建管理员需切到 git 用户，因 Gitea 1.22 禁止 root 运行）：
      ```bash
      kubectl -n devops exec deploy/gitea -- su -c "gitea admin user create --admin --username gitea --password Gitea12345 --email gitea@local.com" git
      ```
    - 为什么：Gitea 轻量、SQLite 免额外数据库，最适合单机最小可用版；管理员命令被 Gitea 拒绝以 root 运行，必须 su 到 git 用户执行。

35. **部署 Jenkins（CI 工具）**
    - 做了什么：namespace `devops`，镜像 `jenkins/jenkins:lts-jdk17`，PVC 20Gi，Ingress host `jenkins.127.0.0.1.nip.io`。
    - 遇到：Pod 内连不上 `updates.jenkins.io`，初始化页面显示"离线"，于是选择"跳过插件安装"直接进入后台。
    - 关键命令（取初始密码，位于 `/var/jenkins_home/secrets/initialAdminPassword`）：
      ```bash
      kubectl -n devops exec deploy/jenkins -- cat /var/jenkins_home/secrets/initialAdminPassword
      ```
    - 为什么：先把 Jenkins 装起来进后台，插件源问题留待后续（内网需配国内插件源或离线导入）。

36. **部署 ArgoCD（CD 工具）**
    - 做了什么：namespace `argocd`，用官方 `install.yaml`（经 `ghfast.top` 代理下载）。因 9443 是 HTTP 端口而 ArgoCD server 默认走 HTTPS，给 `argocd-server` 启动参数加 `--insecure` 关掉内部 TLS，再配 Ingress（host `argocd.127.0.0.1.nip.io`，走 HTTP）。
    - 关键命令（取初始管理员密码）：
      ```bash
      kubectl -n argocd get secret argocd-initial-admin-secret -o jsonpath="{.data.password}" | base64 -d
      ```
    - 为什么：ArgoCD 是 GitOps 的 CD 核心；入口走 HTTP，就必须让 server 也走 HTTP 才能对上，否则浏览器会报 SSL 错误。

37. **安装 buildkit 构建引擎**
    - 做了什么：`nerdctl build` 需要 buildkit 后端（之前报 `buildctl not found`）。下载 buildkit v0.16.0 二进制，写 systemd service（关键参数 `--containerd-worker-namespace=k8s.io`，让构建产物直接进 K8s 使用的命名空间）。另给 buildkit 单独配 `/etc/buildkit/buildkitd.toml`：docker.io 走 `docker.m.daocloud.io` 加速、Harbor 走 http+insecure。
    - 为什么：buildkit 有独立配置，不读 containerd 的镜像加速；不配镜像加速与 insecure，build 会卡在 load metadata。

38. **在 Gitea 建 demo-app 仓库并推送示例应用**
    - 做了什么：用 Gitea API 建公开仓库 `demo-app`。示例应用是"静态网页 + nginx"（`index.html` + `Dockerfile FROM nginx:alpine`），外加 `deploy/` 目录放 K8s 部署清单（deployment / service / ingress）。
    - 为什么：`deploy/` 目录就是 ArgoCD 要监听的 GitOps 清单目录，代码和部署声明放同一个仓库便于统一管理。

39. **手动构建并推送镜像（验证 CI 核心动作）**
    - 关键命令：
      ```bash
      nerdctl build -t harbor.127.0.0.1.nip.io:9443/devops/demo:v1 . --insecure-registry
      nerdctl push harbor.127.0.0.1.nip.io:9443/devops/demo:v1 --insecure-registry
      ```
    - 结果：Harbor 的 `devops` 项目里出现 `demo:v1`（24.86MiB）。
    - 为什么：先手动跑通"构建镜像 → 推仓库"这两个 CI 核心动作，确认链路无误，后续再考虑自动化编排。

40. **创建 ArgoCD Application 实现自动部署（CD 闭环）**
    - 做了什么：编写 Application yaml，`repoURL` 用**集群内部 Service 地址** `http://gitea.devops.svc.cluster.local:3000/gitea/demo-app.git`（关键：ArgoCD 在 Pod 内不能用 `127.0.0.1.nip.io`，必须走 K8s Service DNS），`path=deploy`，`syncPolicy` 开启 automated + selfHeal + CreateNamespace。
    - 结果：apply 后 Application 变 **Synced + Healthy**，`demo` 命名空间自动创建、Pod Running，浏览器访问 `http://demo.127.0.0.1.nip.io:9443` 正常显示页面。
    - 为什么：这一步把 GitOps 的 CD 闭环打通——Git 里的清单一提交，ArgoCD 就自动同步到集群，无需人工 apply。

## 三点五、完整流水线闭环演示（改代码→自动上线）

> 这一节把整条链路端到端演示一遍，模拟"开发改了代码，上线全自动"。

**完整链路（改代码 → 自动上线）**：

1. 改 `index.html`（v1 → v2，并补上 `<meta charset="utf-8">` 修复中文乱码）。
2. `nerdctl build` 构建 `demo:v2` 镜像 → `nerdctl push` 推到 Harbor。
3. 用 `sed` 把 `deploy/deployment.yaml` 里的镜像 tag 从 `v1` 改成 `v2`。
4. `git commit + push` 把改动推回 Gitea。
5. `kubectl -n argocd patch application demo-app` 加一个 refresh 注解，催 ArgoCD 立即同步（默认每 3 分钟才轮询一次）。
6. ArgoCD 检测到 Git 变化 → 自动拉取新清单 → 滚动更新 Pod → 浏览器刷新看到 v2。

**这段命令流程的意义**：整个过程里，我没有手动去 `kubectl apply` 部署，也没有手动改集群里的任何资源——只改了代码和 Git 里的部署清单，剩下的"上线"动作全由 ArgoCD 自动完成。构建镜像那步（CI）当时还是手动跑（2026-09 更新：CI 自动化已在本地 VM 补齐，见《04》），但"更新清单 → 部署到集群"这段（CD）已经全自动。

**一句话总结**：这就是 GitOps——**以 Git 为唯一真相源，声明式地把集群状态同步到和 Git 一致，开发只管提交代码，上线全自动。**

## 五、知识点整理（面试可直接答）

> 每个知识点按"是什么 + 为什么 + 面试怎么答"来记。

### 1. firewalld 与云安全组的区别
- **是什么**：firewalld 是**本机防火墙**，管的是这台服务器自己的进出流量；安全组是**云平台层的网络 ACL**，管的是进出这台云主机的网络访问。
- **为什么**：真正的第一道门其实是**安全组**——流量得先过安全组才能到你的机器。
- **面试怎么答**："firewalld 是操作系统本机的防火墙，安全组是云厂商在网络层做的访问控制，真正拦在最外层的是安全组。学习环境我把 firewalld 关了减少干扰，靠安全组只放行需要的端口（比如 22）。"

### 2. SELinux 三种模式
- **是什么**：enforcing（强制，违规就拦）/ permissive（宽容，只告警不拦）/ disabled（关闭）。
- **getenforce 与 setenforce 的区别**：`getenforce` 查当前状态；`setenforce 0` 是**临时**改成 permissive/关闭，重启就失效；要**永久**关闭得改 `/etc/selinux/config`。
- **面试怎么答**："SELinux 有强制、宽容、关闭三种模式。setenforce 0 只是临时生效，重启会还原，要永久关闭得改 /etc/selinux/config 里的 SELINUX=disabled。"

### 3. dnf/yum 软件源与缓存
- **是什么**：dnf（新）/yum（旧）是 RedHat 系的包管理器，从"软件源"下载安装包并处理依赖。
- **`dnf clean all` + `makecache` 的作用**：先清掉旧的源缓存，再重新拉取生成新缓存，保证装包时用的是最新的源信息。
- **面试怎么答**："换了源或者源信息过期时，先 dnf clean all 清缓存再 makecache 重建，避免拿到过期的包列表。"

### 4. Docker 镜像加速原理
- **是什么**：`registry-mirrors` 是**拉取代理**，配在 `/etc/docker/daemon.json`。
- **为什么**：直接拉 Docker Hub 慢，配国内加速地址走代理更快。
- **注意**：改完必须 `systemctl daemon-reload` + `systemctl restart docker` 才生效。
- **面试怎么答**："镜像加速就是在 daemon.json 里配 registry-mirrors，相当于给 Docker Hub 配了个国内代理，改完要 daemon-reload 再重启 docker 生效。"

### 5. K8s 为什么弃用 Docker
- **是什么**：K8s **1.24 移除了 dockershim**，容器运行时直接用 **containerd**。
- **为什么**：dockershim 是 K8s 为了兼容 Docker 额外做的一层适配，维护成本高，去掉后直接对接 containerd 更干净。
- **节点排查工具**：用 **nerdctl** 或 **crictl**，不再用 docker 命令。
- **面试怎么答**："K8s 1.24 之后移除了 dockershim，节点上的容器运行时是 containerd，排查容器直接用 crictl 或 nerdctl，所以 K8s 节点其实不需要装 Docker。"

### 6. Region 与 AZ 的区别
- **是什么**：Region（地域）是**跨城市**的，AZ（可用区）是**同城不同区县**的机房。
- **延迟**：跨 Region 几十到上百 ms；同 Region 跨 AZ 只有 1~3ms。
- **为什么**：AZ 之间的电力、空调、光纤是物理隔离的，一个 AZ 挂了不影响另一个，这是**高可用的基础**。
- **面试怎么答**："Region 是不同城市，AZ 是同城的不同机房、物理隔离。同城多 AZ 部署延迟低又能容灾，是做高可用的常见做法。"

### 7. 多地多中心的价值
- **是什么**：多个机房分布在不同地方。
- **价值**：**就近接入**（用户访问最近的机房，快）+ **异地备份容灾**（一个地方出事另一个顶上）。
- **机房互联**：机房之间走运营商对称专线，大厂用 **DCI**（数据中心互联）。
- **面试怎么答**："多地多中心一是让用户就近访问降低延迟，二是异地容灾，机房之间用专线打通。"

### 8. 环境划分
- **是什么**：dev（开发）/ test（测试）/ poc（概念验证）/ pet（宠物/临时）/ uat（用户验收）/ pre（预发布）/ prod（生产）。
- **plat**：平台工具类环境，专门放 Jenkins、ArgoCD、监控这些工具。
- **面试怎么答**："环境一般分开发、测试、预发、生产等，另外会单独有个 plat 平台环境放 CI/CD 和监控工具，跟业务环境隔离开。"

### 9. 网络隔离基线
- **原则**：默认**全内网不出网**；dev 完全隔离；test/prod **只有网关节点（Ingress）**允许出网。
- **面试怎么答**："默认所有环境都不出公网，开发环境完全隔离，测试和生产只在 Ingress 网关节点开出网口子，减少暴露面。"

### 10. 命名规范的意义
- **意义**：从名字就能看出机房、可用区、环境、用途，**故障定位快、自动化好写**。
- **K8s 资源名长度限制**：Service **63 字符**，Deployment/ConfigMap 等 **253 字符**。
- **面试怎么答**："统一命名能让人一眼看出资源属于哪个机房、环境、用途，写脚本也方便。注意 K8s 里 Service 名最长 63 个字符，其他资源大多是 253。"

### 11. 中间件规划
- **三种模式**：public（公共共用）、某项目独占、某类项目共用。
- **原则**：**核心业务库要独占**，避免互相影响。
- **面试怎么答**："中间件按重要性分级，一般业务可以共用一套，核心业务的数据库单独独占，防止别的业务把它拖垮。"

### 12. 每个机房独立 Harbor 的原因
- **原因**：跨机房拉镜像慢，所以**每个机房放一个自己的 Harbor**，就近拉取。
- **面试怎么答**："镜像仓库按机房就近部署，避免跨机房拉镜像慢，每个机房一套 Harbor。"

### 13. Sealos 是什么
- 一键部署 K8s 的工具，**对标 kubeadm**，能把整套集群和插件打包起来一条命令装好。

### 14. Calico 是什么
- **CNI 网络插件**，负责 **Pod 之间的通信**（给每个 Pod 分配网络、打通跨节点访问）。

### 15. Helm 是什么
- **K8s 的包管理器**，相当于 K8s 世界的 apt/yum，用 Chart 把一堆 YAML 打包，一条命令装一整套应用。

### 16. containerd 与 nerdctl 的关系
- **nerdctl** 是 containerd 的命令行工具，用法**接近 docker**，习惯 docker 命令的人上手很快。

### 17. 存储三件套（面试高频）
- **链路**：PVC（申请存储）→ StorageClass + 制备器（**nfs-subdir-external-provisioner**）→ **动态创建 PV** → 绑定。
- **面试怎么答**："应用通过 PVC 申请存储，StorageClass 配好制备器（比如 NFS 的 nfs-subdir-external-provisioner），系统就会自动创建对应的 PV 并和 PVC 绑定，实现动态供给，不用手动建 PV。"

### 18. Ingress 的作用
- 集群的**流量入口 / 七层网关**，把外部请求按域名、路径转发到集群内部对应的 Service。

### 19. 时间同步为什么对 K8s 至关重要
- **原因**：K8s 组件之间用**证书校验**，时间偏差过大集群就起不来。
- **工具**：chrony；`chronyc sources` 查同步源。
- **面试怎么答**："K8s 组件之间靠证书通信，各节点时间必须一致，偏差大证书校验就过不了、集群起不来，所以要用 chrony 做时间同步。"

### 20. hostname 与 /etc/hosts 对 K8s 的作用
- 节点靠**主机名**标识，主机名必须**唯一且能解析**，所以要设置 hostname 并在 /etc/hosts 里写好映射。

### 21. 单节点 K8s 必须去掉 master 的 taint（污点）
- **原因**：master 默认带污点，不让业务 Pod 调度上去；单节点只有 master 一台机器，不去掉污点业务 Pod 会**一直 Pending**。
- **面试怎么答**："单节点集群只有 master，得把 master 的 NoSchedule 污点去掉，业务 Pod 才能调度上去，否则一直 Pending。"

### 22. tmux 会话保持
- **用途**：长任务放 tmux 里跑，**断线不中断**。
- **命令**：`tmux new -s 名字` 新建、`tmux attach -t 名字` 重新接入。

### 23. 污点 Taint 与容忍 Toleration
- **是什么**：污点打在**节点**上，表示"普通 Pod 别调度过来"；容忍写在 **Pod** 上，表示"我能接受这个污点"。
- **为什么**：K8s 默认给 master 打 NoSchedule 污点保护控制面，系统组件（kube-proxy、calico）自带容忍所以能跑；单节点集群必须去掉该污点，否则业务 Pod 会一直 Pending；GPU 节点等专用节点也常用污点做隔离。
- **面试怎么答**："污点是节点级别的排斥标记，容忍是 Pod 级别的接受声明。master 默认有污点保护控制面，系统组件靠自带容忍才能调度上去。单节点得去掉污点业务 Pod 才跑得起来，专用节点也常用污点+容忍做隔离。"

### 24. containerd 的命名空间概念
- **是什么**：containerd 有 namespace 隔离，K8s 使用 `k8s.io`，nerdctl 默认查 `default`。
- **为什么**：所以必须指定 namespace（配 `namespace = "k8s.io"` 或 `-n k8s.io`）才能看到集群镜像。
- **面试怎么答**："containerd 内部有命名空间隔离，K8s 的镜像都在 k8s.io 里，nerdctl 默认看的是 default，所以不指定 namespace 就看不到集群镜像。"

### 25. containerd 镜像加速与 Docker 的区别
- **是什么**：containerd 通过 `/etc/containerd/certs.d/<域名>/hosts.toml` 配置多个 mirror。
- **为什么**：按顺序尝试、失败自动切换下一个，比 Docker 的 `registry-mirrors` 更灵活，可以做故障转移。
- **面试怎么答**："containerd 的加速是在 certs.d 下按域名建 hosts.toml，可以配多个 mirror 依次尝试、失败自动切换；Docker 是在 daemon.json 里配 registry-mirrors，containerd 这种更适合做故障转移。"

### 26. hostNetwork 的作用与代价
- **是什么**：Pod 直接使用**宿主机网络栈和端口**（Ingress 因此能占用 80/443，外网可直连）。
- **代价**：端口冲突风险和网络隔离性下降。
- **面试怎么答**："hostNetwork 让 Pod 共享宿主机网络，好处是能直接占宿主机端口、外网直连，代价是有端口冲突风险、隔离性差。生产环境更常用 LoadBalancer 或 NodePort + 外部 LB。"

### 27. Ingress 与 IngressClass
- **是什么**：Ingress 是**七层路由规则**（按域名/路径把请求转给不同 Service）；IngressClass 指明由**哪个控制器**来实现。
- **为什么**：Ingress 本身只是规则，必须有 Ingress Controller（如 ingress-nginx）才生效。
- **面试怎么答**："Ingress 是七层路由规则，按域名和路径转发到不同 Service；IngressClass 说明这条规则由哪个控制器实现。光有 Ingress 不行，必须部署了 ingress-nginx 这类控制器规则才生效。"

### 28. Pod 排障标准流程（面试高频）
- **流程**：`kubectl get pod` 看状态 → `kubectl describe pod` 看 Events（调度失败/拉镜像失败/挂载失败）→ `kubectl logs` 看容器日志 → 必要时 `kubectl exec` 进容器。
- **常见状态含义**：Pending（无法调度或资源不足）、ContainerCreating（拉镜像/挂载中）、ImagePullBackOff（镜像拉不到）、CrashLoopBackOff（容器反复启动失败）、Completed（Job 正常结束）。
- **面试怎么答**："先 get pod 看状态，再 describe 看 Events 定位是调度、拉镜像还是挂载的问题，然后 logs 看应用日志，必要时 exec 进去看。状态上 Pending 是调度不上、ImagePullBackOff 是镜像拉不到、CrashLoopBackOff 是容器反复崩。"

### 29. NFS 动态存储链路
- **链路**：Pod 提交 PVC → StorageClass 指定的制备器监听到 PVC → 调用 K8s API 动态创建 PV 并在 NFS 上建子目录 → PVC 与 PV 绑定。
- **默认 StorageClass**：通过注解 `storageclass.kubernetes.io/is-default-class` 指定，PVC 不写 `storageClassName` 时就用它。
- **面试怎么答**："应用提交 PVC，StorageClass 配的制备器监听到后自动创建 PV 并在 NFS 上建子目录，然后 PVC 和 PV 绑定。设了默认 StorageClass 的话，PVC 不写 storageClassName 就自动用它。"

### 30. SIGHUP 与会话保持
- **是什么**：SSH 断开会给前台进程发 SIGHUP，导致进程退出。
- **解决方式**：tmux/screen（会话保持，可重连查看）、`nohup &`（忽略 HUP 后台运行）、`systemd-run`（托管给系统）。
- **面试怎么答**："SSH 一断，前台进程收到 SIGHUP 就被杀了。长任务要放 tmux/screen 里，或者 nohup 后台跑、systemd-run 托管，这样断线也不影响。"

### 31. 时间同步对 K8s 的重要性
- **是什么**：组件间基于证书通信，节点时间偏差过大会导致证书校验失败、集群异常。
- **为什么/工具**：用 chrony 同步，`chronyc sources` 查看，云上一般自动指向内网 NTP。
- **面试怎么答**："K8s 组件靠证书通信，时间偏差大证书就校验不过、集群会出问题。用 chrony 做时间同步，chronyc sources 看同步源，云上一般自动指内网 NTP。"

### 32. 云上带宽计费的两种模式
- **是什么**：按固定带宽（包月付带宽费，速度有保障）vs 按使用流量（只按实际流量收费，带宽峰值仅作上限）。
- **为什么**：后者提高峰值不增加固定成本，且入方向流量免费，适合学习和流量波动大的场景。
- **面试怎么答**："带宽有按固定带宽和按流量两种。按固定带宽是包月保速度；按流量是用多少算多少，峰值只是限速上限，调高不多花固定钱，而且入方向下载免费，练习环境用这种更划算。"

### 33. Harbor 的组件构成与作用
- **是什么**：core（核心 API 与认证）、portal（Web UI）、registry（真正存镜像的 Docker Registry）、registryctl（registry 管理）、database（PostgreSQL 存元数据）、redis（缓存与任务队列）、jobservice（异步任务：镜像复制、GC、扫描）、trivy（镜像漏洞扫描，可选）。
- **为什么**：Harbor 本质是在 Docker Registry 之上加了一整套企业能力。
- **面试怎么答**："Harbor 是在 Docker Registry 之上加了认证鉴权、项目隔离、UI、镜像复制、漏洞扫描、审计等企业能力。核心组件有 core 做认证和 API、portal 做界面、registry 真正存镜像、database 存元数据、redis 做缓存、jobservice 跑异步任务，trivy 做漏洞扫描是可选的。"

### 34. 私有镜像仓库的价值
- **是什么**：自建在内网的镜像仓库（如 Harbor）。
- **为什么**：镜像不出内网（安全合规）、拉取速度快（同机房）、可做权限隔离与审计、支持镜像复制做多机房分发。
- **面试怎么答**："私有仓库好处是镜像不出内网更安全合规、同机房拉取快、能做权限隔离和审计，还能靠镜像复制做多机房就近分发。"

### 35. Harbor 项目的公开与私有
- **是什么**：公开项目任何人可拉取；私有项目拉取需认证。
- **为什么/怎么配**：K8s 拉私有镜像需要创建 **docker-registry 类型的 Secret**，并在 Pod 里配 `imagePullSecrets`。
- **面试怎么答**："Harbor 项目分公开和私有，公开的谁都能拉，私有的要认证。K8s 拉私有镜像得先建一个 docker-registry 类型的 Secret，再在 Pod 或 ServiceAccount 里配 imagePullSecrets。我这次把项目设成公开，就省掉了这一步。"

### 36. containerd 如何信任 HTTP/自签证书仓库
- **是什么**：在 `/etc/containerd/certs.d/<仓库地址含端口>/hosts.toml` 中声明 `server` 与 `capabilities`，HTTP 仓库需 `skip_verify = true`。
- **为什么**：默认只信任 HTTPS + 受信任证书的仓库，HTTP/自签必须显式放行。Docker 的等价做法是 daemon.json 里的 `insecure-registries`。
- **面试怎么答**："containerd 要信任 HTTP 或自签仓库，得在 certs.d 下按仓库地址（含端口）建 hosts.toml，写 server、capabilities，HTTP 的还要 skip_verify=true。Docker 是在 daemon.json 配 insecure-registries。生产环境应该用 HTTPS + 受信任证书，不该用 skip_verify。"

### 37. 镜像命名规则
- **是什么**：`仓库地址[:端口]/项目名/镜像名:标签`。
- **为什么**：推送前必须用 tag 打上完整的仓库地址，否则会被默认推到 Docker Hub。
- **面试怎么答**："镜像全名是仓库地址加端口、项目名、镜像名、标签。推之前要 tag 成带完整仓库地址的名字，不然默认就推到 Docker Hub 去了。"

### 38. Helm 的作用与常用命令
- **是什么**：把一组 K8s 资源打包成 Chart 并参数化。
- **常用命令**：`helm repo add/update`、`helm search repo`、`helm install`、`helm upgrade --reuse-values --set k=v`（只改指定参数、保留其余）、`helm uninstall`。
- **面试怎么答**："Helm 是 K8s 的包管理器，解决 yaml 复用和参数化部署问题。常用 repo add 加仓库、install 装、upgrade 升级，我这次用 upgrade --reuse-values --set 只改了域名和 externalURL 两个参数，其他保持不变。"

### 39. SSH 端口转发（本地转发）
- **是什么**：`ssh -L 本地端口:目标地址:目标端口 用户@跳板机`，把本地端口的流量通过 SSH 加密隧道转发到远端；`-f` 后台运行、`-N` 不执行远程命令。
- **为什么**：内部系统（数据库、管理后台）不暴露公网，运维通过跳板机/隧道访问，这是标准安全实践。
- **面试怎么答**："SSH 本地转发就是 ssh -L 本地端口:目标:端口 连跳板机，把本地端口的流量走加密隧道转到远端。生产里数据库、管理后台这些不开公网，运维都是通过跳板机做隧道访问，这是标准做法。我这次也是用它绕过了备案拦截。"

### 40. ICP 备案与云上合规
- **是什么**：中国内地服务器用域名提供 Web 服务必须完成 ICP 备案（阿里云还需接入备案）。
- **为什么**：未备案会被云厂商在网关层拦截。
- **面试怎么答**："国内服务器用域名对外提供 Web 服务必须先做 ICP 备案，不然阿里云会在网关层拦掉。临时规避可以走隧道/内网这种不经过公网 HTTP 的路径、用 IP 加高端口直连，或者用境外/香港节点。正式上线还是得老老实实备案。"

### 41. nip.io 等泛解析服务
- **是什么**：把 IP 编码进域名自动解析（如 `xxx.127.0.0.1.nip.io` 解析为 127.0.0.1）。
- **为什么**：学习和测试环境下免去买域名和改 hosts 的麻烦。
- **面试怎么答**："nip.io 是个泛解析服务，把 IP 写在域名里就能自动解析成那个 IP，比如 harbor.127.0.0.1.nip.io 就解析到 127.0.0.1。测试环境用它可以不用买域名、也不用改 hosts，很方便。"

## 八、成本与操作提醒

- 按量付费是**按小时计费**，长时间不操作要在控制台用"**停止（节省停机模式）**"，避免白白扣费。
- 实例释放时**系统盘随实例释放**，避免残留计费。
- **root 密码不要外泄**；练习结束后记得**释放实例**。
- 当前访问方式依赖 **SSH 隧道**：每次重连服务器后需重新执行 `ssh -L 9443:127.0.0.1:9443 root@<公网IP>`（或 `ssh -fNL` 后台运行）才能用浏览器访问各组件。
- 阿里云按量付费实例使用"**节省停机模式**"停机后，**非弹性公网 IP 会释放**，重新开机 IP 会变化；由于组件访问域名用的是 127.0.0.1 泛解析，**IP 变化不影响组件配置**，只需用新 IP 重建 SSH 隧道。
- **短时间离开（1 小时内）不建议停机**，重连成本高于省下的费用；长时间不用再停机。
